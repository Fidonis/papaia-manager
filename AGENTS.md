# papaia-manager — project context

This document provides structural and architectural context for contributors and automated tooling working in this repository.

---

## What this project does

papaia-manager is a web-based control plane for the papAIa stack's addon lifecycle. It provides a browser UI for discovering, installing, starting, stopping, removing, and upgrading papAIa addons. It wraps `papaia-ctl` as a subprocess for all mutating operations and imports `lib.*` modules directly from the mounted papAIa workspace for read-only state queries.

It also serves the stack dashboard: a tile overview of the deployed applications, held in `manager/tiles.yaml` in the papAIa config directory and editable in place by administrators. Next to the links a group can hold **widgets**, cards that show live state (the age of the last backup, the fullest disk, how many services run, the number of open warnings, the installed release, the nearest certificate); each refreshes on its own and a card that cannot read its data says so (see the Dashboard widgets section below).

When the core's optional RAG system is active (profile `rag` in the core `.env`'s `COMPOSE_PROFILES`), administrators also get a computed "RAG" tile group on the dashboard (Qdrant) and a "RAG" category in the sidebar (pages of the manager only, no link out). `core/rag.py` owns this: it reads the profile and `QDRANT_PUBLIC_URL` and never tests whether the URL key exists, because the core keeps it while the profile is off. The tile is added in `_gather_tiles` at render time and is not persisted to `tiles.yaml`; the sidebar gates the whole category wrapper on the profile alone (`rag_enabled`, `templating.py`), so no empty caption remains and a missing URL key does not hide a page. The ingester's own web interface (removed in `qdrant-ingest` 1.0.0) has no tile and no entry: its jobs, runs and credentials are the Ingest Jobs pages. The RAG pages need a core that ships the `rag` profile (papAIa 1.5.0 or newer) and, for their ingest features, `qdrant-ingest` 1.0.0 or newer (see the RAG ingest jobs section below).

Another surface, Connections (`/connections`), is listed before Collections and manages the vector database connections of the RAG system: create, edit, test and delete them, with the connection `default` (the integrated Qdrant) created automatically, editable and marked as the default. They are stored in the ingester's own store, `ai/rag/catalog/connections.yaml`, so the ingest service uses them unchanged (see the RAG connections section below). Collections (`/collections`), the next surface, manages the Qdrant collections of the selected connection (the default one unless another is chosen) of the RAG system and the Keycloak roles that may use them: list, create and delete collections, and keep any number of role names with the access level `r` or `rw` per collection. It is admin-only and exists only while the `rag` profile is active (a 404 otherwise, after the role check). The roles are stored in the format `qdrant-mcp-rbac` defines, so the MCP server enforces them unchanged (see the RAG collections section below).

A page after those two, Embedding (`/embedding`), puts files into a collection through the ingester: files are uploaded into a staging folder that is deleted after a successful run, or picked in the documents folder, and embedded either as "add and update" (nothing is deleted) or as "replace the collection". The run is the ingester's, and its status is read from it (see the RAG embedding section below).

One page after it, Ingest Jobs (`/ingest/jobs`), manages everything else the ingester does, in five tabs (Jobs, Runs at `/ingest/runs`, Credentials, Leftovers and Catalog file): its jobs (create, edit, pause, run, delete with their runs), their runs with live progress and the file-by-file result, the credentials of remote sources (stored encrypted), the leftovers of deleted jobs, and the catalog file with its defaults. They are another editor of `jobs.yaml`, next to the Embedding page and a person with a text editor, and, up to `qdrant-ingest` 0.3.0, the ingester's own interface (see the RAG ingest jobs section below).

Backup / Restore (`/backup`) drives the stack-level `papaia-ctl` commands: `backup` as an ordinary job, `restore` in a detached container that outlives the manager (see the Restore model section below). The same page schedules backups from inside the manager (see Backup schedule below). It was called Maintenance up to 0.2.0; the old paths redirect, and the REST prefix is still `/api/v1/maintenance/`.

Upgrade (`/upgrade`) moves the deployment to a newer papAIa release. It is split in two: a read-only check that resolves the target tag, gates the active add-ons against it and lists the pending migrations, and the upgrade itself, which runs `papaia-ctl upgrade` in a detached container (see the Upgrade model section below). The page also lists the Docker images an upgrade leaves behind and removes them on request.

Audit (`/audit`) reads, exports and prunes the audit log the other surfaces already write to — filtered, paginated JSON/HTML, CSV/JSONL export, and a dry-run-gated prune, all admin-only and CSRF-checked like every other mutating route.

Host (`/host`) reports memory, CPU, GPU, clock synchronisation, disk space and certificate expiry of the machine underneath the deployment, and what Docker's data takes. It measures nothing itself: it runs the core's `doctor` for the six checks it needs, and in a run of its own for `docker_usage`, and shows the core's verdicts (see the Host health section below). How often it measures is a setting (Settings, "Host monitoring"). Admin-only, like Services; the sidebar status row carries its counts to every role.

Models & Usage (`/models`) shows which models LiteLLM serves and what they consumed: tokens, spend and requests per day and per model, for a window of UTC days that defaults to the last seven, as stacked bars with a metric switch, a share list, a table of every model and a page per model. It reads LiteLLM's HTTP API with its master key and changes nothing there; models, prices, teams and keys stay in LiteLLM's own Admin UI, which the page links to (see the Models and usage section below). Admin-only, like Services and Host.

Settings (`/settings`) holds the manager's own configuration in `$PAPAIA_CONFIG_DIR/manager/settings.yaml`, one section per topic: Branding (the name and second line at the top of the sidebar, and an uploaded logo) and Host monitoring (the interval of the Host page's measurements). Admin-only and CSRF-checked like every other mutating route, with every change audited; the logo is the one thing every role fetches, because the sidebar shows it (see the Settings and branding section below).

Users (`/users`) manages the accounts of the bundled Keycloak: list, create (with roles and a first password), enable and disable, roles, password reset, and the sessions of an account. Its second tab, Roles (`/users/roles`), manages the realm's roles: create, change what a role contains, delete. It is reserved for `MANAGER_IDENTITY_ADMIN_ROLE`, a tier above the admin role, and acts with the signed-in account's own Keycloak token rather than a credential of the manager's own (see the User management section below).

Mail has two tabs. Notifications (`/mail`, `/api/v1/notifications`) tells recipients of the administrator's choice by email or webhook when a job failed, a backup is overdue, a service is unhealthy, an update is available or a certificate is expiring, each recipient choosing its own events (see the Notifications section below). Mail Server (`/mail/server`, `/api/v1/mail`) sets up the stack's outbound mail relay, the core's optional `smtp` profile: it edits the mail server behind it (host, connection security, port, login, write-only password, sender; stored with the relay on or off), tests the connection to that server, sends a test mail through the relay and shows its state and queue. The relay is switched on and off in Settings > Modules, not here. A change is a queued job that asks the core's own `setup` to store the values and, while the relay is on, recreates the relay and puts it into Keycloak's realm as its mail server, which is what makes the Users page offer "email a link" (see the Mail relay section below). Admin-only, like Services and Settings; it needs a core with the relay (papAIa 1.6.0 and newer).

Services (`/services`) reports the declared state of the deployment against the live one. Containers come from a single unfiltered `docker ps -a`, partitioned by `com.docker.compose.project` into the core stack and the active add-ons, grouped by their `de.fidonis.module` label and scored from their healthcheck. The declared half comes from the Compose files themselves — core fragments filtered by `COMPOSE_PROFILES`, add-on fragments named by `deployment.yaml` — so a service that was configured but never started renders as *not deployed* rather than vanishing. The page also drives lifecycle: one Compose profile at a time via `papaia-ctl start`/`stop --profiles=`, several profiles at once, or the whole stack in a detached container (see the Service group control section below). The same snapshot drives the status row in the sidebar of every page, for every authenticated role; its popover keeps the core stack and the add-ons apart and adds a row for the host.

That snapshot is also the single Docker reading behind the add-on surfaces: `state.compute_status` takes its set of running Compose projects from `StackSnapshot.running_projects` rather than issuing a `docker ps` of its own, so `/addons` and `/services` cannot disagree about whether an add-on is up.

Authentication is handled natively via OIDC Authorization Code Flow with PKCE against Keycloak. Three configurable realm roles gate access in tiers: the identity role (`MANAGER_IDENTITY_ADMIN_ROLE`) opens Users and holds the admin role as well, the admin role reaches every other surface, and the user role reaches the dashboard only. Authorization is enforced by the route dependencies, so the JSON API is restricted exactly like the pages.

### OIDC Authorization Code Flow

```
Browser → /auth/login
  Manager: generate state + PKCE pair → store in session
  Manager: 302 → Keycloak (OIDC_ISSUER_KC_AUTH)

Browser ← Keycloak login dialog
Browser → /auth/callback?code&state
  Manager: verify state, exchange code+verifier for tokens (OIDC_ISSUER_KC_TOKEN)
  Manager: validate id_token via JWKS (OIDC_ISSUER_KC_CERTS)
  Manager: require admin OR user role, else 403 without a session
  Manager: store refresh token in the session for silent renewal
  Manager: set session cookie → 302 to the remembered `next`, else /

Browser → POST /auth/logout   (the sidebar's "Sign out" form, field `csrf_token`)
  Manager: check the CSRF token (form field or `X-CSRF-Token` header)
  Manager: POST refresh token + client credentials to the realm's logout endpoint
           (derived from OIDC_ISSUER_KC_TOKEN, `core/keycloak_users.logout_url`)
  Manager: drop the cached access token, clear the session cookie → 303 /auth/login
Browser → /auth/login → Keycloak shows its login form (the SSO session is over)
```

Consequences worth remembering when touching sign-out:

- **Clearing the manager's cookie is not signing out.** The redirect to `/auth/login` goes straight to Keycloak, and while Keycloak's SSO session lives it answers with a code without asking for anything. So the manager ends that session itself (`OIDCClient.end_session`), with the refresh token the session already holds: no redirect URI has to be registered for the client, nothing is added to the cookie, and the realm template needs no change. The same call ends the SSO session for the rest of the stack (LibreChat and the others sign in against the same realm); their own application sessions run until their tokens expire.
- **The logout endpoint is only derived for a Keycloak realm.** `logout_url` accepts exactly the shape `admin_endpoint` accepts (`…/realms/<realm>/protocol/openid-connect/token`), and `OIDCClient.end_session` returns False without one: another provider's logout endpoint cannot be guessed, and the refresh token must not go to a guess. The session is then ended locally only.
- **A Keycloak that cannot end the session does not keep the user signed in.** The failure is a warning in the log (without a token), and the manager's own session is cleared regardless. A session Keycloak no longer knows (`400 invalid_grant`) counts as ended.
- **The form posts the CSRF token as a field.** A plain HTML form cannot set a header, so `verify_csrf(request, form_token)` accepts either, compared as bytes. A route that is the target of a form takes `csrf_token` as `Form()` and passes it on; `tests/test_auth_logout.py` pins the field, the header, a wrong or non-ASCII token and the missing GET.
- **There is no `GET /auth/logout`.** It would end the SSO session of everybody whose browser loads a link. A POST without any session (an expired session in a stale tab) is not an error: it goes to the login page.
- **Verified against a real Keycloak.** In a browser against a throwaway Keycloak (26.7) imported from the core's realm template, with the manager reaching it over the address it uses for tokens: the sign-out form posts, Keycloak answers the logout call with 204 and holds no session for the account any more, and the redirect to `/auth/login` shows Keycloak's login form. Before the change the same form answered 403, and the old GET variant went through Keycloak and back to the dashboard without a login form while Keycloak kept the session. Repeat this when the token endpoint's address, the client's settings or Keycloak's logout endpoint change.

### Job model

All mutating operations (install, start, stop, upgrade, remove, uninstall, catalog refresh, backup) run as `Job` objects through a single-flight FIFO queue backed by a single asyncio worker. A scheduled backup is enqueued onto the same queue. Only one mutating job runs at a time. An embedding run is deliberately not a job: it lives in the ingester, and a run of hours must not hold up a backup or an add-on action. Job state and output are persisted under `$PAPAIA_CONFIG_DIR/manager/jobs/`.

**Remove.** `papaia-ctl addon remove` only marks an add-on inactive and leaves its containers running, so the Remove job runs `addon stop --clean-up` first (volumes stay) and then `addon remove`; a failing stop leaves the add-on active. The route and the job both refuse (409) when the add-on's `docker-compose.yml` is missing. papaia-ctl pins `-p <add-on>` for its Compose calls, but without that file Compose takes `COMPOSE_PROJECT_NAME` from the core `.env`, and the `down` hits the core stack, this manager included. Stop, restart and uninstall do not have this guard here; the fix for them belongs to the core (`Fidonis/papaia#244`, merged for the release after 1.6.0, so a core up to 1.6.0 still has the hazard).

**Output streaming.** `_stream_subprocess` in `core/ctl.py` reads the child's output in 64 KiB chunks and puts the lines together itself, because `async for` over the pipe raises when one line is longer than the reader's 64 KiB limit, and a classic image build prints its pull progress as one line of escape sequences without a newline (`Separator is not found, and chunk exceed the limit` failed the job). The pending bytes are a `bytearray` searched from where the last search stopped. A line past `MAX_LINE_BYTES` (1 MiB) is yielded cut at that length with `TRUNCATION_MARKER` appended (the cut never leaves half a multi-byte character before it) and the rest of that line, up to its newline, is dropped, wherever the newline arrives. Every yielded line goes verbatim into the job log, so the cap also bounds the log. `tests/test_ctl_stream.py` pins the chunking, the cap and the order of the output.

### Add-on components

An add-on's `version` counts changes to the bundle, not to the software in it. The catalog states that in the manifest's `components` list (`id`, `name`, `role`, `kind`, `image_var`, `version`, `source`, `pinned: false` for a floating tag), and `core/components.py` turns it into what the gallery card (the primary components next to the add-on version) and the detail page (a table of all of them) show, and into `components` in the add-on JSON of `api_addons`. For an installed add-on each component also carries the version of the managed snapshot (`changed` when the catalog differs, so an update reads "3.0.5 → 3.1.0") and, when the add-on's `.env` in the config directory sets the component's `image_var` to another tag, that tag as `override_version`. The overrides are read from the file, not from `docker compose config`, so the pages need no Docker and no process per view; a different registry with the same tag is not told apart, because the manifest records no repository. The manifest may come from any catalog, so nothing is trusted: entries of the wrong shape are skipped, an unknown role counts as a sidecar, text is cut, at most 32 entries are read and only an `https://` source becomes a link. A catalog without `components` shows nothing extra.

### Upgrading and rolling back an add-on

The decisions belong to `papaia-ctl addon upgrade` and `addon rollback` (papAIa core 1.8.0, ADR 0008 there); this repository stages the files, shows the plan and keeps `installed.yaml` true. Pages: `/addons/<name>/upgrade` (the review), the Versions card and the rollback dialog on the detail page, the Upgrades tile and list on the gallery, and the dot on the Add-Ons nav entry (`/partials/nav/addon-upgrades`).

- **A version is a directory, written once.** `snapshots.managed_snapshot_path(workspace, catalog, add-on, revision)` is `addons/_managed/<catalog>/<revision>/<add-on>`, with the add-on's name last because Compose names the project after it. The revision is `sha[:12]` of the catalog clone's HEAD, or `local-<timestamp>` for a local catalog (a working directory, no commit). `addon_upgrades.stage_revision` never overwrites a directory that exists, and an install uses it too. An install made before this layout is registered at `_managed/<catalog>/<add-on>`; the first upgrade leaves it as it is (it becomes `previous`) and the next one prunes it. `snapshots.prune_snapshots` keeps what is kept (registered directory, `previous`, a version being reviewed) and fills up to three with the newest; `uninstall` removes all of them.
- **The registration is the truth, not installed.yaml.** What runs from where is `path` in deployment.yaml, which an upgrade and a rollback repoint. Everything that needs the installed directory goes through `snapshots.installed_addon_dir(deployment_entry, ...)`; `managed_snapshot_path` without a revision is only the fallback for an add-on deployment.yaml does not list. After a job, `sync_installed_after_upgrade` / `sync_installed_after_rollback` make installed.yaml say what is registered, whatever the exit status: `addon upgrade` that cannot recreate the containers has already moved the registration. `InstalledAddon.history` (three entries, newest first) is provenance for the page, never an input to papaia-ctl.
- **The plan is papaia-ctl's.** `POST /{name}/upgrade-plan` stages the version and runs `addon upgrade --dry-run --json --path=<staged>`; `parse_plan_output` finds the document in the merged output (a lone `{` line) and a plan the gate refused (`blocked`) is still a plan. The review page draws it; nothing about it is computed here, so the page and the upgrade cannot disagree. A POST because it writes (the staged directory, pruning).
- **What was reviewed is what is applied.** The plan returns `revision`; the upgrade body carries it back. For a git catalog a changed HEAD, and for a local one a missing directory, is a 409 "review again". A refusal before the job exists (core too old, gate `blocked`, `in_place`, a key the plan does not ask about, a value `needs_input` lacks) is an HTTP error, not a failed job.
- **Values go through a file.** `write_answers_file` writes `KEY=VALUE` lines to a `mkstemp` file (0600), the job passes `--answers-file=`, and the file is deleted in the job's `finally`. Only keys the plan asks about (`answerable_keys`: new `change_me` and `replace_secret` keys) are accepted, checked against the candidate's own `.env.example` form. The audit entry has the keys (`answered`), never a value.
- **Rollback is one step.** `previous_version` reads `previous` from deployment.yaml and whether its directory and its restore point (the backup catalogue) still exist; the dialog makes the operator choose between code and configuration only and code plus the data of the restore point (`--restore-data`), and the second is not offered without a restore point. Both are audited as `rollback`; `upgrade` is audited with `from`, `to`, `revision`, `backup`, `answered`.
- **Needs core 1.8.0.** `core_supports_upgrades` looks for `cmd_addon_upgrade()` in the core's `addon.sh` (a version number would be wrong for a checkout that has the change before the release). An older core gets a 409 from the routes and a hint on the pages.
- **The upgrade rule is SemVer precedence** (`resolve.update_available`, shared with the notification and the dashboard): a catalog that is behind offers nothing, and a version that is not SemVer counts as an upgrade when it differs. The nav dot and the count come from the catalogs on disk through `addon_upgrades.outdated_count` (a minute of cache, cleared by a catalog refresh or an upgrade); there is no network.
- **The changelog is best effort.** `changelog_between` reads the staged add-on's `CHANGELOG.md` (Keep a Changelog headings, `## [x.y.z] - date`) and returns the sections newer than the installed version up to the candidate, at most about 6000 characters; the page shows them as plain text. An add-on without the file, or one in another format, shows no card.
- **A scoped restore point is not a backup of the stack.** `backup.yaml` entries of `addon upgrade` carry `scope: [addon:NAME]`; `RestorePoint.is_scoped` marks them in the list, `POST /maintenance/restore` answers 409 for one (papaia-ctl refuses it too), the wizard presets "choose what to restore", and `newest_successful` (the status strip, the dashboard widget, the schedule's retention guard) skips them.
- **Not done:** the compatibility verdict is not shown on the gallery (only the review page asks papaia-ctl), there is no "catalogs refreshed N minutes ago" line (a catalog records no refresh time), the catalogs carry no signature, so there is no "verified" mark, and a catalog that needs authentication is refreshed as before.

### Restore model

Restore is the one mutating operation that is **not** a job, and the reason is structural rather than stylistic.

`papaia-ctl restore` calls `docker compose down` on the core project before it unpacks any archive, and `papaia-manager` is a service of that same project (`papaia/src/manager/docker-compose.yml`, profile `manager`). A restore running in this process would be SIGKILLed the moment teardown removed its own container — after the stack is down and before anything was put back. `--no-restart` is not an escape: it overwrites volumes underneath live processes.

So `core/runner.py` starts `papaia-ctl restore -y` in a **separate container**, built by cloning the manager's own container spec (`docker inspect` of the container carrying `de.fidonis.module=papaia-manager`): same image, binds, user and supplementary groups. Cloning rather than re-deriving means path parity and docker.sock access hold by construction and the compose fragment stays the only place those mounts are declared.

State lives in Docker. The runner is started without `--rm` and with `--restart no`, so after it exits `docker inspect` still yields its status and exit code and `docker logs` still yields its output — readable by a manager container that was removed and recreated mid-operation. A progress file could not do this: restore replaces `$PAPAIA_CONFIG_DIR` wholesale. The durable cross-restore record is papaia-ctl's own `backup.log` in the backup directory, which is never restored over.

Consequences worth remembering when touching this area:

- `ALLOWED_CORE_VERBS` in `core/ctl.py` contains `backup`, `backup-delete`, `start`, `stop`, `restore-scoped` and `keycloak-role-sync`, and deliberately **not** `restore`: `restore-scoped` requires a selection and refuses `--restart-clean` in papaia-ctl itself, so it cannot replace `$PAPAIA_CONFIG_DIR`, and `backup-delete` and `keycloak-role-sync` run no `docker compose` command (the first needs an explicit restore point, the second applies what the realm template says to the running Keycloak and is idempotent).
- Backup and restore are mutually exclusive, enforced in `routers/api_maintenance.py` with 409s.
- The restore-point id is validated against an exact timestamp pattern before it reaches a path join or an argv.
- `PAPAIA_BACKUP_DIR` must be mounted at its host path, or the catalogue is invisible to the container.

### Upgrade model

Upgrade is the second mutating operation that is **not** a job, for a stronger version of restore's reason: `papaia-ctl upgrade` runs `cmd_stop --clean-up --addons` between its two phases, unconditionally and unscoped. It also `exec`s itself from the target release's tree after moving the checkout, so it cannot be a streamed in-process job even setting the teardown aside.

The read half and the execute half are deliberately separate.

**The check** (`core/upgrade.py`) never changes anything and is split by cost. `current_version`, `checkout_state` and `read_upgrade_log` are file reads plus three local `git` calls, cheap enough to render on page load. `run_check` fetches from the remote and materialises a `git worktree` of the target tag, because the add-on gate has no honest answer without one — only the target's tree carries its own `ADDON_API` window and its Compose service names. It is an explicit operator action, serialised behind an `asyncio.Lock`, and its result is cached for the process. The fetch runs in the manager container, which has no SSH client or key, so an SSH `origin` is fetched through its HTTPS equivalent (`https_equivalent`, passed as a URL — the checkout's configuration is never written). A fetch that still fails is a warning carrying the commands from `fetch_hint`, never "the newest release": the page and the header button say "Could not check" / "Check failed" instead.

The arithmetic itself is delegated straight back to the core: `ALLOWED_PY_COMMANDS` in `core/ctl.py` allows `upgrade-resolve`, `upgrade-plan` and `addon-check` (and, for other pages, `doctor`, `render-preview` and `module-info`), invoked through `run_py_cli` as `python3 -m lib.cli` with the workspace on `PYTHONPATH` — the same shape `papaia-ctl` uses for itself. Parsing four lines of TSV is the price of the manager and a shell on the host never reaching different verdicts about the same checkout. `upgrade-record` is deliberately absent: it writes the migration ledger, and only the upgrade's own second phase may do that.

**The upgrade** goes through `core/runner.py` as a third `RunnerKind`, next to restore and stack. `--version` is always pinned, never omitted: without it papaia-ctl means "go to whatever is newest", and a tag published between the operator reading the migration list and clicking the button would move the deployment somewhere nobody reviewed. It also makes the runner name deterministic, which is the real mutual exclusion — `docker run` refuses a duplicate name.

Consequences worth remembering when touching this area:

- `ALLOWED_CORE_VERBS` deliberately does **not** contain `upgrade`, and `ALLOWED_PY_COMMANDS` is a separate set with no overlap.
- The manager upgrades itself. The target release pins its own `papaia-manager` image in `papaia/src/manager/docker-compose.yml`, so the `up` at the end of phase 2 recreates this container from a different image than the runner was cloned from. The session survives (`setup --env-only` keeps `MANAGER_SESSION_SECRET`); the page an operator returns to does not — the success strip tells them to reload.
- Phase 2 therefore runs the *new* core's Python under the *old* image's interpreter. Fine today; there is no manager-side mitigation if a future core raises its Python floor.
- `/partials/upgrade/runner` is a **frozen path**. A tab open across the upgrade keeps polling the URL baked into the previous image's markup, so renaming it would leave that tab on a 404 for the whole outage.
- An upgrade is mutually exclusive with every job, restore and stack action, and the guards are symmetric — `api_maintenance.py` and `api_stack.py` refuse while an upgrade runs, not just `api_upgrade.py`.
- A finished upgrade runner is **not** cleared automatically the way a stack runner is. It holds the outcome of the last attempt, and `$CONFIG_DIR/upgrade.log` is what makes dismissing it safe.
- There is no automatic rollback, by design in papaia-ctl. The failure panel renders `_upgrade_failed`'s recovery block verbatim rather than re-deriving it.
- A dirty checkout blocks the upgrade with no override. `--force` degrades the add-on gate only, and is refused outright when the gate passed or failed on an `ERROR`.
- The target version reaches both an argv and a container name, so it is validated with `\Z`-anchored patterns in both `core/upgrade.py` and `core/runner.py` — `$` would also match before a trailing newline.

**Image cleanup.** `papaia-ctl upgrade` pulls the target's images through `docker compose up` and never removes the ones it replaced. `core/images.py` finds them, and it does so without the previous release's tree: an image is *outdated* when it is neither *declared* nor *used* and every reference it carries lives in a repository the stack declares. Declared is `docker compose config --images`, run the way papaia-ctl runs compose — the core file with every override in the config directory (the LocalAI GPU override swaps a tag, which reading the YAML would miss) and each installed add-on, active or not, with its own env file. Used is the image of every container on the host, stopped ones included. The repository condition is what keeps it from being `docker image prune -a`; the per-image (not per-repository) declared check is what keeps `postgres:16` next to `postgres:18.3`.

- **Fail closed.** If any source's declared images cannot be resolved the report carries the reason and no candidate. Removal never uses `-f`, so the daemon's own refusal is the last line of defence.
- `POST /api/v1/upgrade/images/prune` recomputes the candidates under a lock and treats the request's ids as a narrowing, never a widening. It is refused while an upgrade, restore, stack runner or job is running; a *finished* upgrade runner does not block it.
- The option is `prune_images` on `POST /api/v1/upgrade`, off by default at the API and preselected in the dialog. With it, `build_upgrade_run_args` wraps papaia-ctl in a small shell (`runner._UPGRADE_WITH_PRUNE`) that runs `python -m app.core.images prune` only after a zero exit and always exits with papaia-ctl's status: a failed cleanup must not turn a successful upgrade into "upgrade failed". The runner carries the label `de.fidonis.upgrade-prune-images`, which is how the phase list knows to show the step and how a later manager finds out what it was started for.
- The runner container holds the *previous* papaia-manager image, so that one cannot go during the run. `POST /runner/clear` therefore repeats the cleanup after removing a successful, labelled runner. A failed run is never cleaned up.
- Known limits: an image of a service a release drops entirely stays (its repository is no longer declared), and sizes are the images' own, so shared layers are counted twice.

### Backup schedule

The Backup page can start backups on a schedule. The schedule is one file, `$PAPAIA_CONFIG_DIR/manager/schedule.yaml` (`core/schedule.py`), and the only source of truth: `core/scheduler.py` runs APScheduler 3.x with a **memory** job store and is rebuilt from the file, so a removed schedule cannot come back from a second store after a restart. APScheduler 4.x is not an option while every 4.x release is an alpha.

The scheduler decides *when*. The backup itself goes through `core/backup_run.enqueue_backup`, the path the button uses, so the job, its log and its audit entry (`user=scheduler`, `params.trigger=schedule`) are the same. What differs is the refusal: the button answers a busy queue, a running restore or upgrade, or an unmounted backup directory with a 409, while a scheduled run is skipped (audit `backup.schedule.skip`, result `skipped`) and retried every 10 minutes, up to six attempts. It cannot simply be queued behind the other work, because a restore or upgrade is not in the queue.

Consequences worth remembering when touching this area:

- **Standard cron, not APScheduler's dialect.** APScheduler 3.x counts weekdays from Monday (`0 3 * * 1` fires on *Tuesday*) and ANDs a restricted day-of-month with a restricted weekday, where cron ORs them. `parse_fields` rewrites weekdays to names and refuses the combination; a test pins the Monday case. Never hand an expression to `CronTrigger.from_crontab`.
- **Cadence is neutral across clock changes.** Around one, the wall clock and elapsed time disagree: a daily 03:00 is 24, 23 or 25 hours apart, and an hourly schedule is 2 hours apart on the wall clock across the spring change and runs twice at 02:00 across the autumn one. `analyse_cadence` measures the shortest gap in elapsed time, so an hourly schedule is not refused in a zone with daylight saving time, and takes the longest as the larger of each gap's smaller reading, so "daily" stays 24 hours and the retention floor and the overdue limit do not move with the season. Its loops step through real instants (`_after`), never `run + 1 s`: a zoned datetime forgets which side of a clock change it is on when it is added to, and the walk would go back into the hour that repeats. A time that does not exist on the day the clocks spring forward is shown where it happens (02:30 becomes 03:30).
- **Known limit: the hour that repeats.** APScheduler 3.x runs a fixed time inside the hour the clocks repeat twice on that day (02:30 CEST and 02:30 CET). With the single-flight queue that is a second backup an hour later, once a year, and it is not worked around. `test_a_fixed_time_inside_the_repeated_hour_runs_twice_on_that_day` pins the behaviour, so a fixed APScheduler fails it and the note can go.
- **The timezone is part of the schedule**, defaulting to the container's `TZ` and then UTC, and `tzdata` is a dependency so `zoneinfo` works on any base image and in tests on Windows.
- **One margin everywhere.** *Overdue* is 1.5 times the longest gap between two runs, and the status strip, the catch-up at start and the retention guard all read the same `overdue_after`.
- **Catch-up reads the catalogue, not memory.** The manager restarts on every upgrade, restore and reboot, and a memory job store cannot know a slot was missed. At start, if the newest restore point with `result == ok` is older than the limit, one run is queued 120 seconds later. A `partial` restore point is usable but is not a success.
- **Retention is held back while the newest success is overdue.** `papaia-ctl backup` prunes after every run, a failed one included, and `prune()` keeps no last usable restore point, so a long series of failed backups would delete every good one. `plan_retention` passes `--retention-period-days` only while a recent `ok` point exists, and the job log says when it did not. In the schedule the retention is at least 1 day and at least twice the longest gap; `0` is not allowed.
- **A damaged `schedule.yaml` is reported, never read as "no schedule".** `load_schedule` returns the reason, the page shows it, and `DELETE` clears the file.
- **PUT and DELETE are refused while a restore or upgrade runner runs** (they replace `$PAPAIA_CONFIG_DIR`, and a schedule written meanwhile would be overwritten with the state being restored), and PUT is refused without a reachable backup directory. A restore also returns `schedule.yaml` to the state of the restored snapshot.
- **`AsyncIOScheduler` binds to the loop it is created in**, so it is built in the startup hook, after the job queue, and a failure to start costs the schedule and not the manager. Its `shutdown()` runs a turn later and keeps reporting `running`, so `BackupScheduler.shutdown` is idempotent on its own flag.
- **The scheduler assumes one process.** The image runs a single uvicorn worker; with `--workers` every worker would fire.
- **The editor's preview is its validation.** `GET /partials/backup/schedule/preview` runs the same checks as the PUT, compiles the presets (daily, weekly, every N hours) to cron on the server and carries the result in hidden fields, so the page script holds no copy of those rules and Save sends what was previewed.

### Service group control

A **service group** is one Compose profile. That is the granularity, because it is the only one `papaia-ctl` accepts — there is no per-service verb. The mapping to modules is many-to-many and read out of the fragments, never derived from the name: `librechat-websearch` covers `firecrawl`, `searxng`, `jinaai` and `mcp-firecrawl`, while `oauth2-proxy` is labelled `papaia-auth`. `inventory.core_groups` is the authority, and the set it returns is the allowlist a request is validated against — a profile that is not in `COMPOSE_PROFILES` is absent from it, and `papaia-ctl` would otherwise hand `docker compose` a profile whose env file setup never rendered.

Two execution models, split on whether the operation removes the container serving the request:

- **Group actions** (`POST /api/v1/stack/groups/{start,stop,restart}`) name profiles explicitly and never `manager`, so they are ordinary queued jobs. `ctl.profiles_flag` builds the `--profiles=` flag and refuses `manager` regardless of what the caller passed.
- **Stack actions** (`POST /api/v1/stack/{start,stop,restart}`) cover every profile including `manager`, so they go through `core/runner.py` in a detached container, exactly like restore. `runner.RunnerKind` keeps the two runner flavours apart by label and name prefix. The outcome is read back from `docker inspect` / `docker logs` by `/partials/stack-runner`.

Further points that are easy to get wrong:

- `restart` is composed as stop → start. papaia-ctl has no restart verb, and adding one would mean a change in the stack repo plus a minimum-version coupling.
- `--clean-up` (`docker compose down` instead of `stop`) attaches to anything that stops — a stop, and the stop half of a restart, where it turns the operation into a full recreate. It is **rejected with 400** on start, which has no such flag; ignoring the field there would confirm an operation that did not happen. After a stop with it the page reports the modules as *not deployed*: a removed container is indistinguishable from one that was never created.
- A stack action never passes `--addons`. That flag exists and would take every add-on down with the core stack — the bulk action this surface deliberately omits. Add-ons are started, stopped and restarted one at a time.
- The selection state lives in an Alpine scope in `services.html`, **outside** `#service-list`. That element is swapped every 15 s, and state held inside it would not survive a single poll — nor would an open confirmation dialog.

### Host health

The Host page and the chip's Host row read the machine, not the containers, and they read it from the core. `app/core/host_health.py` runs `doctor --json` through `run_py_cli` and keeps only `memory`, `cpu`, `gpu`, `time_sync`, `disk_space` and `certs`; the other five checks fork `docker`, resolve names and probe ports, which is not something to repeat on a poll, so they are skipped by name and the answer is filtered to the six that were asked for. A check the core adds later is ignored rather than shown unreviewed.

Consequences worth remembering when touching this area:

- **The verdict is the core's.** Its disk thresholds are free bytes (warn below 10 GiB, fail below 2 GiB) and its certificate thresholds are days (30 and 7); memory, CPU and VRAM have limits of their own in the core. The percentage drawn next to a row is for the eye and never picks a colour; a threshold of this panel's own would let it and a shell on the host disagree about the same disk. For memory, CPU and VRAM the core states the reason for a warning only in its summary sentence, so that sentence is shown as is on the row. Changing a threshold is a change in the core.
- **The skip list may only name old checks.** `--skip` refuses a name the core does not know, so `_SKIPPED_CHECKS` holds only checks every core with `doctor` has, and a new check is requested by *not* skipping it. A 1.4.0 core that predates one simply has no row for it.
- **Not measured is not empty.** The manager mounts the config and backup directories, not `/var/lib/docker`, so the Docker data root is normally absent from `doctor`'s answer. The page has no row for its free space, because a row that only said "not measurable" read as a hole where a reading belonged; what Docker holds is shown under "Docker usage" instead. A data root the core can measure is an ordinary disk row. An unreadable certificate has no verdict and is left out of the counts. A resource check the core reports as `skip` is a row that says "Not measurable from this panel" and carries the core's reason, and is left out of the counts the same way. The one exception is a `gpu` skip with no details at all: nothing is configured to measure (no LocalAI, or the CPU image), so it gets no row. A core that predates `Fidonis/papaia#210` skips `gpu` and `time_sync` whenever `doctor` runs inside a container, which is where the manager runs it, so against such a core those two rows read as not measurable; a core that can read them there fills them in from the same fields.
- **Not knowing is not the same as bad.** A core without `doctor` (checked as the existence of `lib/doctor.py` in the workspace, not as a version comparison), a timeout, an unparseable answer and a refused argument all yield `available=False` with a reason. The chip leaves the host out of its headline in that case, the way it leaves out an empty add-on section.
- **Exit 2 is a result.** `doctor` exits 2 when a check failed and still prints the whole document. Exit 2 with nothing on stdout is a refused argument (for instance a skipped check the core renamed), and its first stderr line becomes the reason.
- **Reading is cheap, running is not.** `load_host_health` serves a reading for the refresh interval (60 s by default; 15 s for a failure, or the interval if that is shorter) and runs at most one `doctor` at a time; concurrent callers share the task. The run belongs to the process, not to the request that started it, and is shielded, so a visitor who closes the tab does not cancel it for the next one. "Re-check" bypasses the interval but not a five-second minimum interval.
- **One interval, set in Settings.** `host.refresh_seconds` in `settings.yaml` (10 s to 60 min) is the cache's time to live, the page's poll (rendered into `host.html`'s `hx-trigger`) and, times three with a floor of 180 s, the point where the cache-only consumers stop showing a reading. It is read at every call and judged against the age of the reading, so shortening it takes effect at the next poll. The Host page only displays it. An open page keeps the poll it was loaded with until it is reloaded. The API refuses a value out of range; a hand-edited file is clamped on read, because a validation error would reset every section of the document, the branding included.
- **Docker usage is measured apart.** `app/core/docker_usage.py` runs `doctor` for the `docker_usage` check alone (every other check in the core's registry is skipped), behind a cache of its own. It is the one check that costs the daemon real work: `docker system df` sizes every volume, which took 1.5 s with 75 volumes and grows with the data. So it is measured every tenth refresh interval, never sooner than 5 minutes and never later than an hour (`usage_interval`); a failed reading is retried after 2 minutes; "Re-check" gets a fresh one at most every 30 s. A visitor waits for it only when there is no reading yet or after "Re-check"; otherwise the last reading is served as it stands and a new run starts behind the page. Its failure or slowness is a note under the disk space and cannot hold up, empty or fail the host reading. It is a report with no verdict, so it is never in the counts, the chip or the dot.
- **The core is asked what it has before it is asked for it.** `doctor` cannot list its checks and `--skip` refuses a name it does not know, so `docker_usage.core_checks` reads the registry out of the core's `lib/doctor.py` (`("name", check_...)` entries) and `docker_usage` is skipped by the host run, and requested by its own, only for a core that has it. An older core gets neither: no run, no section, no refused argument.
- **The chip and the sidebar dot never wait.** They render on every page every 30 s, so they read `cached_host_health()` and ask `ensure_fresh()` for a background refresh. With no page open nothing runs, a cold cache shows no Host row for one poll, and they refresh no faster than every 30 s whatever the interval.
- **Counts only for non-admins.** The chip's Host row says `n / m ok`. Paths, host names and certificate names appear on `/host`, which is admin-only. A test asserts that none of them reaches the chip.
- **`run_py_cli` takes a `limit`.** A child that outlives it is killed and reaped before `CtlError` (exit code 124) is raised. The default is no limit, which the upgrade check relies on.
- **`doctor` is in `ALLOWED_PY_COMMANDS`.** It is read-only by the core's own contract; `tests/test_ctl.py` pins the set.

Known limits: no history (that is what an observability stack is for), no GPU figures and no clock state from inside the manager container from a core that cannot read them there, the free space of the Docker data root (it is not mounted; what Docker holds is shown instead), memory and CPU figures that are the host's own (`/proc/meminfo` and the load average are not namespaced) and not those of any container limit, and thresholds that cannot be tuned from here. Memory, CPU and the clock change faster than disk and certificates, but all of them share one run and one interval.

### Models and usage

The Models & Usage page (`/models`, Monitor group, between Host and Jobs) and its API (`/api/v1/models`, `/api/v1/models/usage`) read LiteLLM, the stack's model gateway. `core/litellm.py` is the client, `core/model_usage.py` the numbers, `core/usage_view.py` the page as data, `core/charts.py` the geometry, and `tests/fake_litellm.py` the in-memory LiteLLM (`httpx.MockTransport`, in the shapes of 1.100) that `test_litellm_client.py`, `test_model_usage.py`, `test_ui_models.py` and `test_api_models.py` run against.

- **Read-only, and provably so.** The client has no method that is not a GET and sends to three routes only: `/health/readiness` (no key), `/model/info` and `/user/daily/activity`. `READ_PATHS` is the whole list; anything else raises before a request is made, and the tests record every request the page causes. The master key is the strongest credential of the stack, which is the reason.
- **The master key is read at request time** from `$PAPAIA_CONFIG_DIR/ai/litellm/.env` (`LITELLM_MASTER_KEY`), like the RAG secrets, so a shell on the host and the manager agree on it and the core needs no change. It goes into one header and nowhere else: not into a message, a log line, an exception text or a page, and `LitellmSecrets` hides it from a `repr`. A message names `host:port` and the exception class, never the address. Without a key nobody is asked anything.
- **Failure is a state, not an error.** A LiteLLM that is down, a key it refuses, an error status or an answer that makes no sense is a `Reading` with a `problem` (a msgid and parameters, so the cached reading is worded in each account's language); the page shows it and offers to try again, the API answers 503. Nothing here raises into a request.
- **Days are UTC days, and the grain is a day.** `/user/daily/activity` has no finer grain, so there is no "today" or "24 hours" window. `7d` is today and the six days before it; `30d`, `90d`, `month` (the first until today) and `custom` (`from`/`to` as `YYYY-MM-DD`, both required, `from` not after `to`, not in the future, at most 365 days) are the others. An invalid window is told to the person who typed it and replaced by the default; the API answers 422. LiteLLM writes usage in batches, so the newest requests trail by about a minute.
- **Paging counts rows, not days.** One day can arrive on several pages and the same model from several keys, so values are added up. A window needing more than `MAX_PAGES` pages is read as far as that and marked incomplete, which the page says.
- **Model names are the public ones.** Usage is read from `breakdown.model_groups`, the names users call, which are the `model_name` of `/model/info`; several deployments behind one name are one model. A name with usage but no deployment is shown as no longer served; a served model with no usage is listed all the same. LibreChat calls LiteLLM with the master key, so there is no attribution by user or team and the page does not pretend to one.
- **No price, no spend.** A model without a price in LiteLLM (a local one) counts tokens and requests and has spend 0. The page shows a dash instead of `$0.00` and says so; a price is set in LiteLLM.
- **One reading per window, shared.** `load_reading` keeps a reading for 60 s (15 s for a failure), runs one fetch at a time per window (concurrent callers share the task), folds a "Reload" inside five seconds of the last reading into it, and keeps at most 16 windows. The cache holds the raw reading, never text.
- **The page's whole state is its query string** (`range`, `from`, `to`, `metric`, `view`, `model`; `usage_view.Query`). Every control is a link to the same page with one thing changed, which htmx swaps into `#models-body` and records as the address, so a view can be bookmarked and the page works without script. The shell loads its body from the query it was asked with.
- **Charts are boxes, not an SVG scaled to the width.** Bars are `div`s with a height in percent, so labels keep the size of the page's text on every width; only the table's trend lines are inline SVG. Colours are the theme's `--chart-0` to `--chart-6` and `--chart-other` (`docker/tailwind.app.css`, one set per theme, validated against the card surfaces): a model keeps its slot from one window to the next, and with more than seven models the busiest keep one and the rest are drawn together as "Other". A chart is never the only way to read a number: the legend, a tooltip that is also reachable with the arrow keys, and the table of days say the same. Tooltip text is set with `x-text`, never as markup.

Known limits: no budgets, teams or keys (LiteLLM's own pages), no attribution by account, no live view (a day is the grain), no export, and no download status of local models. The dashboard has no `model-usage` widget yet.

### Settings and branding

The manager's own configuration is one document, `$PAPAIA_CONFIG_DIR/manager/settings.yaml` (`core/settings_store.py`), with one top-level section per topic: `branding` and `host` today. The uploaded logo lives next to it in `manager/branding/`, so both travel with a backup and come back with a restore. Without the file nothing changes: every field has a default, and the sidebar looks as it always did.

Consequences worth remembering when touching this area:

- **A reading never fails.** A missing file, a missing section, an unreadable document or a section written by a newer release yields defaults, and unknown keys are ignored on read and dropped on the next save. `effective_branding` is what the sidebar renders and it never raises; a settings problem must not take the page down.
- **`None` is not empty.** In `branding`, `None` means "use the built-in default" and an empty tagline is a deliberate "show no second line". `validate_branding` keeps the two apart: a blank name falls back to the default, a blank tagline hides the line.
- **The API is strict, the file is clamped.** `host.refresh_seconds` read from the file is clamped to 10 s to 60 min (and a non-number becomes the default), because a pydantic error would send `load_settings` back to the defaults for the whole document and reset the branding over a number somebody edited by hand. `PUT /api/v1/settings/host` refuses an out-of-range value with a 422 instead.
- **Stale writes are refused.** `revision` is the SHA-256 of the file's bytes (empty when there is none). Saving the branding text, resetting it and saving the host interval carry the revision the page was loaded with and answer 409 when it no longer matches. Uploading and deleting the logo do not. Writes go through a temporary file and a rename.
- **The logo type is decided by its bytes.** `save_logo` looks at magic bytes (PNG, JPEG, WebP, SVG) and ignores the client's filename and `Content-Type`. At most 512 KB are read, one byte past the cap so an oversized body is refused without being buffered. An SVG that contains a script, `foreignObject`, an event handler, `javascript:`, an entity declaration or an `iframe` is refused at upload.
- **The logo is served defensively.** `GET /brand/logo` is open to every signed-in role, since the sidebar shows it to all of them, and answers with `X-Content-Type-Options: nosniff` and `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; sandbox`, so an SVG opened directly by URL cannot run anything. The URL carries the stored filename (`?v=`), which changes with the content, so the one-day private cache cannot show a stale logo.
- **Every change is audited** as `settings.branding.update`, `settings.branding.logo.upload`, `settings.branding.logo.delete`, `settings.branding.reset` or `settings.host.update`, with target `settings`.

### Modules and overlay

Settings has three tabs: Manager (`/settings`, the branding and host monitoring cards), Modules (`/settings/modules`) and Overlay (`/settings/overlay`). The last two and their API (`/api/v1/config`) change how the stack is configured, not how the manager is. `core/config/` holds all of it (`modules` the optional modules and their state, `overlay` the three editable files and their writes, `history` the saved versions, `preview` the core's `render-preview`, `service` the jobs), `routers/api_config.py` and `routers/ui_config.py` the surface, and `tests/test_config_*.py` and `tests/test_api_config.py` pin it.

Consequences worth remembering when touching this area:

- **The core stores the choice, the manager asks it to.** A module is on when its profile is in `COMPOSE_PROFILES` of `$PAPAIA_CONFIG_DIR/.env`; the one writer is the core's `setup` (`--enable-local-ai`, `--enable-web-search`, `--enable-rag`, `--localai-variant`), run through `run_module_setup` with a typed `ModuleSetup` and nothing else (no `--force`, `--env`, host name), and for the mail relay `--enable-smtp` through `run_smtp_setup` (`SmtpSetup(enable=True)` switches it on with the settings the core stored). `localai`, `web-search`, `rag` and `mail` are the switchable modules and this tab is the only place that switches them; `manager` cannot switch itself off. On: `setup`, then `start --profiles=<profile>`, then a wait for the group to be healthy; the RAG system then recreates LibreChat (its rendered configuration lists the RAG tools and is read once), and the relay ends with the realm sync the Mail section describes. Off: `stop --clean-up [--volumes] --profiles=<profile>` while the profile is still active, then `setup --enable-...=false`, then (RAG) the LibreChat recreate, (mail) `keycloak-role-sync`, then the deletion. The page's `revision` (profiles plus LocalAI variant) makes a stale tab a 409.
- **A switch-off has three results, and no fourth.** `scope` is `keep` (containers only), `data` (`stop --volumes` takes the anonymous volumes of the containers with them, then `module-purge --data` removes the named volumes by name) or `all` (`module-purge --data --config` also puts the module's `.env` files back to what the release ships and removes the files it keeps outside them). Settings alone are not a state: the core refuses the RAG system's settings without its data (the ingester's stored credentials are encrypted with `QI_CONNECTIONS_SECRET`, and the ACL collection lives in the Qdrant volume), and a module whose settings went and whose data stayed is of no use. A deletion needs the module's name typed back (`confirm`), checked by the API and not only by the dialog. The dialog is fed by `GET /api/v1/config/modules/{name}/info`, the core's `module-info` (a read-only command in `ALLOWED_PY_COMMANDS`); `module-purge` is the second allowed write command, reachable only through `run_module_purge`, which takes a module name from `PURGE_MODULES`. The core refuses it while the profile is on, so it runs after `setup`. If it fails the module stays off with whatever was not deleted still there and the job says so (audit result `partial`). A core without `tools/lib/modules.py` still switches off and keeps everything (`core_manages_modules`); asking for a deletion there is a 422.
- **Switching on asks what `setup` asks, only where the answer is missing.** The core's `module-info` lists the module's questions (`questions`: the public URL of LocalAI and of Qdrant, with the `setup` option, the default derived from the stack's host and `ask`, true when the stored URL is empty, a placeholder or the shipped one), and the settings reset puts the URLs back to that state, so deleted settings open the question again; a later `setup` run derives the URL from the host and closes it. The questions open inline under the module's row, the same for LocalAI, the RAG system and the mail relay (`panel-<module>` in `settings_modules.html`; no dialog, so nothing covers a phone's screen), and only the open ones are asked, prefilled with the default, and sends the answer as `public_url` (`ctl.public_url` validates it: http or https, a host, no login, query, fragment or `.env`-unsafe character) which becomes `--localai-host` or `--qdrant-host` in `ModuleSetup`; a module without an open question switches on without a dialog, and a core that cannot answer (`available: false`) asks nothing. The mail relay has no core question: its panel opens when no server is stored (`configured`), prefilled from what is stored (`mail_defaults`, never the password), validated with the Mail page's own `validate_input` (its Test Connection button posts the form's values to the Mail page's `/api/v1/mail/probe`, which sends nothing and saves nothing), and goes to `setup` as a full `SmtpSetup` together with `--enable-smtp=true` in one run; the password is scrubbed from the job log and the refusal, and the audit entry says `login_change`, not the value. A refusal is shown in the panel, which stays open so the answer can be corrected.
- **Enabling is asked first, where the core would refuse.** The RAG system is refused while an active add-on named `qdrant`, `qdrant-connect` or `qdrant-ingest` runs the same services (`modules.check_enable` reads `deployment.yaml`; `tests/test_config_contract.py` compares the names with the core's), and the relay is refused without a mail server (`mail_configured`), so the operator reads the sentence before a job is queued. The core checks again. A profile the core's Compose files do not have, or a core without the module operations for RAG and Mail, disables the switch with an explanation instead of failing in a job. A start that fails after `setup` leaves the module switched on in the configuration, and the job's message says so.
- **The LocalAI variant is chosen, never detected.** The core's detection looks at the host from the host; from inside this container it would report nothing. `vulkan` is left out because the core decides its devices by looking at `/dev` while it renders. `tests/test_config_contract.py` compares the offered variants with the core's.
- **Overlay targets are keys, not paths.** `librechat`, `litellm` and `searxng` map to the core's render targets; a request never contributes a path. `keycloak.conf` and `models.txt` are replaced as a whole by an overlay instead of merged, so they are not offered. Other files under `overlay/` are listed as "not editable here" or "ignored by the render" (the render only looks at the exact paths of its target list).
- **A write is compare-and-swap, and the file is the job's to write.** The revision is the SHA-256 of the bytes (empty when there is no file). The route checks it for a quick 409, the job checks it again, and `overlay.write` checks it a third time under a lock immediately before the rename. A symbolic link is refused, a new file is created 0600, an existing mode is kept.
- **Applying means recreating.** The core's render replaces each target with a new file and the containers bind-mount single files, so a restart would keep the old file. The job runs `stop --clean-up` and `start` for the profile (a group that is not switched on only gets the file). If either fails the previous bytes are written back (unless the file was edited meanwhile), the group is started again, and the job fails with the reason (`config.overlay.rollback.auto`). If the group starts but is not healthy within 90 seconds the file stays, the job fails and the audit result is `partial`: the previous version may be no better, so the page offers the roll back and does not take it.
- **The history is written before anything changes.** `history.save` copies the old bytes to `manager/overlay-history/<key>/<UTC stamp>-<apply|discard|rollback>.bak` (0600 in a 0700 directory, latest 20); if it cannot, nothing is changed. A version id is checked against a fixed pattern before it is joined to a path. Restore as draft only fills the editor; Roll back now is a job like Apply and saves the current file first.
- **The core is asked, not copied.** The effective result is the core's `render-preview` (`ALLOWED_PY_COMMANDS`): the draft goes in a 0600 file under `manager/tmp/` that is removed whatever happens, never in an argument. Whether the core has the command is read from its source (`preview.available`), not from a version. Without it the editor still checks the syntax and applies; the job's automatic roll back is the net. A core that cannot be asked is not a reason to refuse an Apply.
- **No content in logs.** Overlay content can hold an API key. Request bodies are read by hand so a validation error never echoes them, the job log and the audit entries carry target, size and revisions only (`config.module.enable|disable`, `config.overlay.apply|discard|rollback|rollback.auto`), and the overlay page embeds no file content (the editor loads it through the API).
- **Stale tabs and busy stacks are 409s.** A restore, an upgrade or a stack action that is running refuses a change (it replaces or migrates the directory the change is written to); an ordinary job does not, the queue runs one at a time.

### User management

The page and its API (`/users`, `/api/v1/users`) manage the accounts of the realm the manager signs in against. `core/keycloak_users.py` is the Admin API client, `core/users_service.py` holds the rules, `routers/users_deps.py` builds both for one request, and `tests/test_users_service.py`, `tests/test_api_users.py`, `tests/test_user_token.py` and `tests/test_keycloak_users.py` pin them, against `tests/fake_keycloak.py`.

Consequences worth remembering when touching this area:

- **There is no credential of the manager's own.** Every call goes to `/admin/realms/<realm>` with the access token of the signed-in account, so Keycloak applies that account's rights and nothing more. The session keeps only the refresh token; `auth/user_token.py` turns it into an access token on demand, single-flight per refresh token, and caches that token in memory until shortly before it expires. It is never put in the session cookie, a log line or an exception text (`TokenSet` keeps it out of `repr`). The cache assumes one process, like the refresh state in `auth/deps.py`.
- **The role carries Keycloak's rights, the manager only gates the page.** `MANAGER_IDENTITY_ADMIN_ROLE` (default `papaia-admin`) must hold `manage-users`, `view-users`, `query-users`, `view-realm` and `manage-realm` of the `realm-management` client, as a composite (the last is what Keycloak asks for to create, change or delete a role; without it every one of those answers 403, while reading roles works with `view-realm`). `manage-realm` is not limited to roles: it also covers the realm's settings. Where it does not, Keycloak answers 403 and the page shows that as a state, with the way out: add the five roles to `papaia-admin` in the Admin Console (Realm roles, Associated roles, filter by clients), or use a core release whose realm template and role sync (`papaia-ctl start`) do it; a new sign-in picks the change up. The role sync only applies what the realm template defines, so on a core that predates the composite it reports nothing to do. A plain administrator is denied before Keycloak is asked. There is deliberately no allowlist of roles: the role is the highest in the stack. What the page does guard is the lock-out: nobody disables their own account, takes the identity role from themselves or ends all of their own sessions.
- **The address comes from the token endpoint.** `admin_endpoint` reads the base URL and the realm out of `OIDC_ISSUER_KC_TOKEN` (`…/realms/<realm>/protocol/openid-connect/token`), so there is nothing new to configure. An address that is not a Keycloak realm's, or `AUTH_PROVIDER=external_oidc`, means no page (404 after the role check) or a 503 from the API.
- **A refusal and an unreachable Keycloak are states of the page, not errors.** `UsersService.snapshot` returns a view with `state` `forbidden` or `unavailable`; the API answers the same conditions with 403 and 503. A token Keycloak refuses (401) is neither: the session is over, and the browser signs in again.
- **The realm's default role does not carry the dashboard role.** The realm import leaves `default-roles-<realm>` with Keycloak's own roles (`offline_access`, `uma_authorization`) and the account's, not the `user` role the template asks for, so a new account can sign in to Keycloak and use nothing. The New user dialog therefore offers the roles up front with `MANAGER_USER_ROLE` ticked, and the roles are checked before anything is written, so a mistyped one leaves no account behind. Technical roles (`default-roles-*`, `offline_access`, `uma_authorization`) are never offered or touched. A role held through a composite is shown as inherited and can only be removed by changing that role.
- **Passwords.** A temporary password is generated here (`generate_temporary_password`: 20 characters, all four classes, no look-alikes), set with `temporary: true` so Keycloak asks for a new one at the first sign-in, and returned once by the route that makes it, with `Cache-Control: no-store`. It is not in the audit log, any log line, or the page after its dialog closes. The audit log masks values under keys that sound like secrets, so the parameter that records how the first sign-in was arranged is `first_login`, not `credential`. A mailed link (`execute-actions-email`, `UPDATE_PASSWORD`) needs a mail server on the realm; the page reads that from the realm (`smtpServer.host`) and offers the link only then.
- **An account that exists is always recorded.** Creating one is several calls (the account, its roles, its password). If a later one fails, `create` raises `PartiallyCreated`: the route writes `user.create` with `result` `partial`, answers 422 (Keycloak refused the values, for instance a password policy) or 502 with what is missing, and the page reloads the list, because the account is there.
- **A write sends the whole representation.** Enabling and disabling `PUT`s the account as it was read with `enabled` changed: with a declarative user profile a partial body is validated as if the missing fields had been cleared. Disabling also ends the account's sessions, best effort, so a departed employee does not stay signed in until a token refresh happens to fail.
- **Ids are checked before they reach a URL.** A user id is a UUID; a session id is a 24-character base64url string, not a UUID, which a real Keycloak shows and a fake of UUIDs would hide (`tests/fake_keycloak.py` hands out the real format). An account can only end sessions it owns: the session is looked up among the account's own first.
- **An ended session ends at the next renewal.** The manager validates the id token locally and refreshes within a minute of its expiry, so a session ended in Keycloak stops working here at the next refresh, within the access token's lifetime (five minutes in the shipped realm).
- **The dialogs live on the page, not in the list.** The list is replaced after every change and on every search; a dialog that holds a password must survive that. The list partial carries what the dialogs need (whether the realm can send mail, where this page starts) in a marker element.
- **Every change is audited** as `user.create`, `user.enable`, `user.disable`, `user.role.assign`, `user.role.revoke`, `user.password.temporary`, `user.password.reset-email`, `user.session.revoke` or `user.session.revoke-all`, with the username as the target and never a password. An account created with roles leaves both `user.create` and `user.role.assign`. `tests/test_api_users.py` fails when a mutating route is added without being listed there.
- **Verified against a real Keycloak.** The page was driven in a browser against a throwaway Keycloak (26.7) imported from the core's realm template with the composite added: sign-in, creating an account with a temporary password and signing in as it (forced password change, dashboard), enabling and disabling (a disabled account is refused), roles, a mailed link that sets a password, several sessions of one account ended one by one and all together (their refresh tokens then fail), and an account that holds only the admin role being denied. Repeat this when Keycloak's Admin API, the realm template's roles or the token flow change.

### Role management

The Roles tab and its API (`/users/roles`, `/api/v1/roles`) are the same machinery as the accounts: `core/roles_service.py` holds the rules, `routers/api_roles.py` the routes, `routers/users_deps.py` builds the service for one request, and `tests/test_roles_service.py` and `tests/test_api_roles.py` pin them, against `tests/fake_keycloak.py`.

Consequences worth remembering when touching this area:

- **The stack's roles are shown, not changed.** `BUILT_IN_ROLES` mirrors the roles of the core's realm template, and the three roles the manager is configured with (`MANAGER_ADMIN_ROLE`, `MANAGER_USER_ROLE`, `MANAGER_IDENTITY_ADMIN_ROLE`) are added to it. A built-in role has "View" in the list and no delete; the API refuses to change or delete one (422). Services refer to these roles by name, and a deleted `manager-admin` or `papaia-admin` would lock everybody out. A core release that adds a role to its realm template needs it added to `BUILT_IN_ROLES` too.
- **A role is not renamed.** The name is what every service refers to, so a different name is a different role. The dialog shows the name read-only after creation; the role's description and the realm roles it contains are what an edit changes.
- **Composites are a graph, so a loop is refused.** `_reaches` walks the members of the role to be added; a role that already contains the role being edited, or the role itself, is a 422 with the reason. Only the realm roles a composite contains are edited; the roles of clients it also contains (`papaia-admin` carries some of `realm-management`) are listed as "Keycloak admin" and left alone, because their members are not part of the choice.
- **Creating is several calls, and the role is always recorded.** Like an account, a role is created and then given its members; if that second step fails, `create` raises `RolePartiallyCreated`, the route writes `role.create` with `result` `partial` and answers 502 with what is missing, and the dialog reloads the list. Members are checked before anything is written.
- **Deleting says who is affected.** The delete dialog reads the accounts that hold the role directly (the first 100, and whether there are more) and asks for the name. Keycloak removes the role from every account and every composite; the accounts stay.
- **Keycloak keeps its own roles to itself.** `default-roles-*`, `offline_access` and `uma_authorization` are never listed, offered as members or touched, in the list, the New user dialog and the role dialog alike.
- **A right taken away reaches the page with the next token.** Keycloak authorizes by the access token's roles, and the manager caches that token until shortly before it expires (about five minutes), so removing `manage-realm` from `papaia-admin` is noticed at the next refresh, not at once. A refusal says which right is missing and how to add it (`_WRITE_HINT`); reading roles keeps working without `manage-realm`.
- **Every change is audited** as `role.create`, `role.update` or `role.delete`, with the role as the target. `role.update` is written only when something changed, and `tests/test_api_roles.py` fails when a mutating route is added without being listed there.
- **Verified against a real Keycloak.** In a browser against a throwaway Keycloak (26.7) imported from the core's realm template: viewing a built-in role (read-only, with its realm and client members), creating a role with a member, editing its description and members, a loop and a self-containing role refused, built-in roles refused, the new role offered on the Users tab and given to an account, the delete dialog naming that account and keeping the name confirmation, the account staying with its other roles, the role gone from the roles that contained it, and the refusal naming `manage-realm` once the right was taken away from `papaia-admin`. Repeat this when Keycloak's role API or the realm template's roles change.

Known limits: no unlock for an account that brute-force protection has locked, no "last sign-in" (that needs Keycloak's event log), no deletion of accounts (erasing data is a different job from account lifecycle), no federated users, and no bulk import.

### Mail relay

The page and its API (`/mail/server`, `/api/v1/mail`) set up the stack's outbound mail relay, the core's optional `smtp` profile (papAIa 1.6.0 and newer): one internal Postfix relay that holds the credentials of the real mail server and that Keycloak, and add-ons that attach it, send through. `core/mail/` holds all of it (`settings` what the core stored and the rules, `probe` the SMTP conversations, `status` the relay's state from `doctor`, `service` the jobs that apply a change), `routers/api_mail.py` and `routers/ui_mail.py` the surface, and `tests/test_mail_*.py` and `tests/test_api_mail.py` pin it.

Consequences worth remembering when touching this area:

- **The core stores the configuration, the manager asks it to.** The settings live in `$PAPAIA_CONFIG_DIR/.env` (`COMPOSE_PROFILES`), `infra/smtp-relay/.env` (the `SMTP_RELAY_*` keys) and `infra/smtp-relay/upstream-password`, and the one writer is the core's `setup` (`resolve_smtp`), which validates, keeps values sticky, raises `SMTP_RELAY_PASSWORD_REV` when the password changes and edits the profile list. The manager runs it non-interactively through `run_smtp_setup` (`core/ctl.py`) with the options of the relay and nothing else: `ALLOWED_PY_WRITE_COMMANDS` is `{"setup", "module-purge"}`, apart from the read-only commands, and `smtp_setup_flags` builds the argument list from a typed `SmtpSetup`, never passing `--force`, `--env`, a host name or any other part of the stack's configuration. Every value is named when the settings are saved, so what is stored does not depend on what was sticky. `SmtpSetup(enable=None)` stores them and leaves the profile alone (the core keeps the settings whether the relay is on or off), `enable=True` alone switches the relay on with what is stored, `enable=False` switches it off and keeps the settings. A run changes the profile list, the mail files, what the core renders from them (the realm import file, `deployment.yaml`, the checkout's `src/**/.env`) and the time in `deployed.lock`, and nothing a hand edit put elsewhere in the files; `tests/test_mail_contract.py` runs the real `setup` in a copy of the checkout and compares before and after.
- **The password travels in the environment of the child only.** `PAPAIA_SMTP_PASSWORD` is set for `setup` and nowhere else, never in an argument, and the manager's own environment is not inherited into it (an empty value means "keep the stored password" to the core). It is scrubbed from every line that reaches the job log, kept out of `repr`, the audit log and the responses, and a request that cannot be parsed is refused from a hand-made message: a Pydantic error for a missing field would echo the whole body, so `api_mail._body` builds its own. The audit parameter that says what happened to it is `login_change` (`set`, `kept`, `removed`, `none`), not `password`, because the audit viewer masks a key that sounds like a credential.
- **A stored password belongs to its host, port and login.** An empty password field keeps the stored one only while the host, port and login are the stored ones (`stored_secret_applies`), for a save and for the connection test alike; anything else is a 422 asking for the password again, so the manager never carries it to an address somebody typed. `read_password` is read by the connection test and by nothing else.
- **The rules are a mirror, the core wins.** `settings.validate_*` copy `tools/lib/smtp.py` so the page can answer a field at once and the API can refuse before a job is queued; `setup` checks again, and a refusal by the core becomes the job's failure in its own words (`service.refusal`, the `ERROR:` line). `tests/test_mail_contract.py` compares both against the core's own module over a corpus of values and needs `PAPAIA_SRC` (a checkout of `Fidonis/papaia` with the relay, for example `C:\Projects\fidonis\papaia`); it is skipped without it. Run it when either side's rules or option names change. The manager does not import the core's code in a running process: after a core upgrade the module in memory would be the old one.
- **Saving is `setup`, then, while the relay is on, `start --profiles=smtp`.** With the relay off the job only stores the values (audit `mail.settings`); the page says the relay is off and links to the Modules tab, and a core that predates the module operations refuses the save because it would read the values as "switch on". With the relay on, `start` recreates the relay when a value or the password revision changed (Compose's config hash) and ends with the sync that puts the relay in as Keycloak's mail server. The profile is named by hand rather than checked against `inventory.core_groups`, because it joins the profile set during the job. Switching on and off is the Modules tab's job (`config.service`): on is `setup --enable-smtp=true` with no values, `start --profiles=smtp` and the same realm check as above (`mail.service.run_verb`); off is `stop --clean-up --profiles=smtp` while the profile is still active, `setup --enable-smtp=false` (the settings and the password stay unless the operator chose to delete them), then `keycloak-role-sync` (a core verb of its own, in `ALLOWED_CORE_VERBS`), which takes out a mail server the relay set and leaves one that was configured by hand.
- **`start` exits 0 when the realm step did not happen.** It only warns, so the job reads the output (`service.realm_problem`): a line `Keycloak role sync skipped` or `failed` makes the job fail with the reason, after an audit entry with result `partial`, because Users cannot mail links without the realm's mail server. A deployment that does not use the bundled Keycloak skips on purpose (`AUTH_PROVIDER is not internal_keycloak`) and is not a failure. The sync reaches Keycloak from inside the manager's container only with a core that uses the internal address there (`Fidonis/papaia#235`); with an older core every apply from the manager fails at this step after waiting 90 seconds, which is measured, not guessed.
- **Stale tabs and busy stacks are 409s.** The form carries `revision` (a fingerprint of the module env, the profile and the password file's size, so a changed password changes it without the file being read) and a save from an older page is refused (so is a switch of the Modules tab, whose `revision` is the profile set). A restore, an upgrade or a stack action that is running refuses a change (it replaces or migrates the directory the change is written to); an ordinary job does not, the queue runs one at a time.
- **Testing the connection runs here, from the manager's container.** `probe_upstream` mirrors the core's, which `doctor` uses on the host and does not use inside a container. The manager runs it because an operator asked, with the values in the form and without saving, and it reaches the mail server over the same Docker network egress as the relay does. It never attempts a login without encryption. The result is an answer, not an HTTP error: the stage it stopped at (resolve, connect, tls, starttls, auth) and the server's reason.
- **A test mail is handed to the relay, not delivered.** It goes to `smtp-relay:587` (no login, no TLS, as every service of the stack sends), from the stored sender, to an address that is a plain `name@domain.tld`, at most once every ten seconds per process. "Accepted" means queued: the relay retries for a day, and the image refuses recipients whose domain does not resolve, which is shown in the relay's own words. The recipient is not written to the audit log.
- **The status is measured on its own.** `status.load_status` runs `doctor` with every other check of the core's registry skipped (read from `lib/doctor.py`, because `--skip` refuses a name the core does not know), behind a ten-second cache shared by concurrent callers. The host health poll skips `smtp` where the core has it (`host_health._skipped`): the check runs `docker exec` into the relay, and only this page uses the answer. Inside a container the core's check does not contact the mail server.
- **Every change is audited** as `mail.update`, `mail.settings`, `mail.probe` or `mail.test-message`, with target `smtp-relay` (switching the relay on and off is `config.module.enable|disable` with target `module:mail`). A job's audit entry is written when it succeeds (a failed job gets the queue's own `error` entry), and `tests/test_api_mail.py` fails when a mutating route is added without being listed there.
- **Verified against the real code.** The real `setup` in a throwaway copy of the core (the options, the files that change, a named environment, hand edits that survive, a refusal that writes nothing), and a stack of its own in a browser: switching on against a stand-in mail server, the realm's `smtpServer`, a test mail, an upstream that goes down (the queue shows in the status) and comes back, the three kinds of failed handshake, a new password recreating the relay and an empty field not touching it, the password nowhere but in its file, switching off, and a sync that cannot reach Keycloak failing the job. Repeat this when the core's `setup`, its option names or the realm sync change.

Known limits: no queue flush or delete (`postqueue` is the way), the clients allowed to send (`SMTP_RELAY_ALLOWED_CLIENTS`) and a hand-set sender domain are not edited here, the connection test checks the server's certificate against the manager container's trust store and the relay checks it against its own, so a certificate one accepts and the other refuses is possible, and the page does not show what the relay logged.

### Notifications

The first tab of Mail (`/mail`, `/api/v1/notifications`) tells recipients when something needs attention. A recipient is one email address or one webhook URL with a list of the events it chose; the page is a matrix of recipients and events. `core/notifications/` holds the feature (`model` the five events and the rules, `store` the files, `detect` what is true now and what is new, `delivery` the email and the webhook, `service` the background task and the job listener), `routers/api_notifications.py` and `routers/ui_notifications.py` the surface, and `tests/test_notifications_*.py` and `tests/test_api_notifications.py` pin it. The Mail Server tab moved to `/mail/server`; `_mail_tabs.html` is the bar of both.

Consequences worth remembering when touching this area:

- **A recipient owns its subscriptions.** There are no channels or rules to keep consistent: deleting a recipient removes what it chose, and nothing can point at a channel that is gone. The check interval, the debounce and the certificate lead time are global (the detection is shared); they are not per recipient.
- **Two files, two writers.** `manager/notifications.yaml` is what an administrator configured: pydantic with `extra="forbid"`, a sha256 `revision` on every write (a stale tab gets a 409), a lock around read-modify-write, an atomic write created with mode 0600. A file that cannot be used is reported and never replaced (`load_config` returns `error`; every change is then a 409), so a hand edit with a typo is not overwritten by the next tick of a checkbox. `manager/notifications-state.json` is written by the background task and the test button only and holds what was reported (`seen`) and the last test result per recipient (`tests`); it is separate so that the task recording something does not make an open page stale. Both are in the configuration directory, so they are backed up and restored with it.
- **A webhook URL is a secret.** It authorises whoever posts to it, so the API returns `https://host/…` (`model.mask_url`) and a change that omits `target` keeps the stored one; it is in no response, page, audit entry, log line or failure reason (a failure says "the webhook answered 502" or "could not connect", never where). Bodies are parsed by hand (`api_notifications._body`) so a 422 does not echo it. The URL must be http or https with a host and no login; redirects are not followed, the answer's body is never read, and there is no block on private addresses on purpose: a receiver inside the stack's network (n8n, ntfy) is a normal use, and the feature is for administrators, like the mail connection test. The webhook is part of the configuration directory's backups like every other secret.
- **Nothing a job wrote leaves the manager.** A job's log and the text of the exception that failed it can hold a secret, and both would travel to a mailbox or a chat. `job_failed` carries the job id, action, target, who started it and the exit code, and the message is a sentence built from action and target.
- **Edge events, markers and the debounce are `detect.decide`.** It is a function of the conditions found, the remembered state and the settings, and the only place those rules live. `backup_overdue` and `service_unhealthy` fire when a condition turns true and not while it stays true (a service that flaps fires at most once per debounce window); `update_available` and `cert_expiring` fire when their marker changes (the version on offer, the date a certificate expires), so a renewal or a newer release is news by itself and the same one never is twice. A finding is complete only for its `scope`: a pass that could not read the add-ons must not forget `core`. A detector that cannot tell (Docker unreachable and the empty snapshot that comes with it, no `doctor`, a damaged schedule, an unreachable backup directory) returns nothing at all, because an empty finding would clear what is remembered and report it again when the answer returns. The state is stored before the delivery starts: a manager that stops in between loses a notification instead of repeating it.
- **Services are not looked at while the stack is being worked on.** Backups `docker pause` every container while they archive it, a group stop stops it, and a restore or upgrade replaces it; `detect.stack_is_busy` (an active job in the queue, or a restore, upgrade or stack runner) makes the pass skip the service check. `stopped` and `unhealthy` count, and so does `missing` for a module a pass saw running: a stop with "Clean up" (`group-stop`, `clean_up: true`) removes the containers while the profile stays active, and so does `docker rm`, and either is an outage as much as a stopped container. A module that was never seen running is not one (a profile that was enabled and never started is a choice), and neither is `starting`. What a pass saw deployed is `NotifyState.up` in the state file: `detect.service_findings` adds every module in a state that says it was brought up (`healthy`, `starting`, `unhealthy`, `stopped`; not `completed`, `unknown` or `missing`, so a one-shot that ran and exited is not a service), keeps a module that is down known (so a later `missing` still counts) and drops one that is no longer in the snapshot (profile off, add-on removed). `starting` joins on purpose: LocalAI needs a minute to pass its health check, and a service stopped before that was running all the same (the first version only counted `healthy` and missed exactly that). A pass that is skipped (busy stack) or that Docker does not answer leaves `up` as it was, so the stop a job is carrying out is judged by the pass after the job, against what ran before it.
- **Updates cost a network round trip, so they are not looked at every pass.** `upgrade.newer_releases` fetches the release tags and compares them with the deployed version; it does not call `run_check`, which resolves a target and evaluates it in a worktree and overwrites the cache behind the navigation marker and the target an upgrade starts from. It takes the same lock, so two fetches never run over one `.git`. The service asks at most once an hour, and only if somebody chose the event. The add-on half reuses the rule of the add-ons page (`resolve.update_available`, shared so the two cannot disagree) against the catalogs on disk; catalogs are refreshed by hand, so an add-on update shows up after the refresh.
- **Only subscribed events are looked for.** A pass reads the configuration first and runs a detector only if an enabled recipient chose its event: no `docker ps`, `git fetch` or `doctor` for an event nobody receives. The configuration is read again at every pass, and the check interval again every ten seconds while the loop waits (`_wait_for_next`: the next pass is due one interval after the last one began), so a change on the page needs no rescheduling and takes effect within seconds, whether it shortens the wait or lengthens it; an interval read once before a single long sleep would let a change count only after the old one had run out. The task is one asyncio loop that waits between passes (the pattern of `IngestWatcher`), so a pass cannot overlap the next; it is deliberately not a job of the backup scheduler, which is `None` when the backup schedule fails to start. The first pass waits a minute after the manager starts, so containers that are still coming up are not reported.
- **A failed job is reported from the queue.** `JobQueue.add_finished_listener` calls listeners after the lock is released and `finished_at` is set; a listener that raises is logged and goes no further, because an exception that escaped `_worker` would stop the queue. The service hands the report to a task of its own (a strong reference is kept, the loop holds only a weak one). The same listener, for every job that ends and not only a failed one, sets an event that cuts the loop's wait short (`_wake`, cleared when a pass begins, so one that ends while a pass runs asks for another): what a start or stop in the manager did is looked at at once, a stop is reported without waiting out the interval, and a service started and stopped again within one interval is still seen. Restores, upgrades and whole-stack actions run in detached runners outside the queue and are not reported, and a scheduled backup that gave up after its retries only leaves an audit entry; a backup that finished `partial` is not a failed job and shows up as `backup_overdue` once no good backup is recent enough.
- **Delivery is per recipient and written down by name.** `delivery.deliver` never raises: a recipient that fails costs only itself, its reason is a short sentence, and an exception contributes its class name and nothing else (its text can carry an address). Deliveries are audited as `notify.sent` and `notify.failed` by user `notifier` with the recipient's name as target; an administrator's edits are `notifications.recipient.create|update|delete`, `notifications.settings` and (via the test) `notify.*` under their own name, so filtering the log for `notify.` shows deliveries only (the page's "Recent notifications"). Email goes through `mail.probe.send_message` to `smtp-relay:587` like the test mail, and "sent" means the relay took it. It is not tried while the relay is off or not configured: the recipient fails with "the Mail Server is not set up" and the page marks it "Waiting for Mail Server". The sender is the relay's stored sender; header values are one line.
- **A test is a delivery.** `service.send_test` sends a `test` notification to one recipient, records the result in the state (shown as "Test passed", "Test failed" or "Not tested yet"), and is limited to one per recipient every few seconds. A recipient that was saved but never tested is shown as such; nothing forces a test.
- **Stale tabs are 409s, and writes are serialised in the browser.** Every change carries the `revision` of the file it was made on and answers with the new one; the page keeps it and sends changes one at a time (`notifySerial`), because a second tick sent before the first answer would be refused as stale. A refused change says why in a toast (a stale one asks to reload, and a tick that was refused is put back). `tests/test_api_notifications.py` fails when a mutating route is added without being listed there.

Known limits: no reminders while a problem persists and no "recovered" notice, no per-recipient thresholds, a service has to be seen deployed by one pass before its loss can be reported (a pass runs right after every job of the manager, so a start and a stop made there are seen; one started and stopped outside it within one check interval is missed, and so is one while the manager was down for the whole of its run), certificates are only the ones `doctor` scans (the configuration directory's `certs/` and Let's Encrypt's `live/`, not a custom certificate uploaded into Nginx Proxy Manager), `backup_overdue` needs a backup schedule, add-on updates need a catalog refresh, and the email is plain text that names the manager's address without linking to a particular page.

### Internationalisation

The interface is English in the source and German in `src/app/locale/de/`. A **language is a directory**: `src/app/locale/<code>/LC_MESSAGES/messages.po` is discovered at start-up (`app/i18n/catalog.py`), listed in the account menu under its own name (`Locale.parse(code).get_display_name(code)`, so "Deutsch") and used for `Accept-Language` matching (`de-AT` finds `de`). No code, list or setting names the languages. The source language `en` needs no catalogue. The catalogues are read with Babel and compiled in memory; there is no `.mo` build step.

**Which language a request gets** (`i18n/middleware.py`, `i18n/negotiate.py`): the account's stored choice, else the browser's `Accept-Language`, else `MANAGER_DEFAULT_LOCALE`, else `en`. The choice is `POST /account/language` (a plain form with the CSRF field, so it works without JavaScript; `auto` removes the choice). It is stored by OIDC `sub` in `$PAPAIA_CONFIG_DIR/manager/preferences.yaml` (`core/user_prefs.py`), not in a cookie or `localStorage`, so it follows the account to every computer and browser and travels with a backup. The file is separate from `settings.yaml` on purpose: that document has a global revision and answers 409 on a stale write, which a user changing their language must not trigger for an administrator. A damaged file reads as "no preference" and is never overwritten (the change answers 503). The manager does not delete accounts, so an entry of an account removed in Keycloak is harmless and simply stays. The language is a `ContextVar` set by `LocaleMiddleware` (registered before `SessionMiddleware`, so it runs inside it and can read the session), which is why it is also right in macros imported without context, in exception handlers, in HTMX partials and in `/api/*` error messages. `Content-Language` and `<html lang>` carry it.

**Rules when writing a text the user reads:**

- **Templates.** Prose goes in `{% trans %}…{% endtrans %}` (`ext.i18n.trimmed` collapses the whitespace; plurals with `{% pluralize %}`; a variable is named in the tag, `{% trans name=x %}`). An attribute or an expression uses `{{ _('…') }}`. For Alpine, JavaScript and `title`/`x-text` use `{{ _('…')|tojson|forceescape }}`. In `_()` a literal `%` is written `%%`.
- **JavaScript** gets its messages from the `I18N` object in `base.html` or from `tojson`, with `{name}` placeholders filled by `fmt`, `fmtHtml` and `fmtPlural` (which knows `one` and `other`). Never assemble a sentence from pieces (`action + " finished"`): a translator needs the whole sentence.
- **Python, at the place the text is produced**: `from app.i18n import gettext as _`, named placeholders and never an f-string: `_("%(n)s files") % {"n": n}`. Plurals use `ngettext`. A message in an exception or a `HTTPException` is translated where it is raised.
- **Tables at module level** (labels, enum descriptions) use `N_("…")`, which marks the text and returns it unchanged. Translate it where it is shown (`_(label)`). `tests/test_i18n_static.py` fails on `_()` at module level, in a class body or in a default argument, because that runs once at import, in English, and is then shown to everybody.
- **Caches that are read by several people** must not hold a translated text: the widgets' runtime key includes the language, and `host_health` keeps the raw reading and parses it per request.
- **Not translated, on purpose:** log lines, audit parameters, job titles and job logs, notification emails and webhooks, upgrade runner markers, anything the operator or an add-on catalog supplies (tile and branding defaults seeded into a file, add-on descriptions), and what Keycloak or `papaia-ctl` return. Code outside a request runs in English because nothing sets the language there.
- **Never build a sentence from translated words.** If one part of a sentence varies, give each variant its own whole sentence.

**Checks that keep it honest** (`tests/test_i18n_*.py`): `test_i18n_catalog.py` extracts every text from the source with `src/babel.cfg` and, for every shipped language other than `en`, demands that nothing is missing, empty, fuzzy or stale, that placeholders and markup survive, and that plurals have the language's number of forms; a language added later is checked without touching the test. `test_i18n_templates_coverage.py` lints the templates for English text outside `{% trans %}` and `_()` (words that are not prose, such as product names, are in `ALLOWED_WORDS` in `tests/i18n_scan.py`). `test_i18n_static.py` forbids translation at import time. `test_i18n_routes.py` covers the picker, the store across two "computers" with the same `sub`, `next` validation, HTMX partials, the 403 page, `/api/*` errors and a render of every page in German.

**Changing a text**, adding a text or adding a language: see "Add or update a language" in `CONTRIBUTING.md`. After any change to a user-visible text, extract and update the catalogues, translate what is new, and run `tests/test_i18n_*.py`.

### Default tile icons

The default tiles carry an icon that ships with the manager, so the dashboard never loads an image from another site for them. `DEFAULT_ICONS` in `core/tiles.py` maps the casefolded tile name (LibreChat, LiteLLM, Keycloak, NGINX Proxy Manager, Qdrant) to a file under `src/app/static/icons/`, and `default_icon(name)` reads it. The seed (`_DEFAULT_TILES`) writes the path into a new `tiles.yaml`; `_resolve_tile` falls back to it by name for a stored tile without an icon, so an installation whose `tiles.yaml` was seeded earlier (the file is seeded once and never rewritten) gets the icons too; an `icon` set on the tile wins. The computed Qdrant tile (`core/rag.py`) sets it itself, and the editor receives `default_icons` in its draft payload so its store (`iconFor`) shows the same icons. A tile the operator renames loses the fallback, because the match is by name.

The directory is the one place for third-party files. `NOTICE.txt` needs an entry for every `.svg` (the file name alone at the start of a line, the source pinned to a commit or tag, the licence, the owner of the mark), `LICENSE-dashboard-icons.txt` holds the licence text, and `tests/test_icon_assets.py` fails for a file without an entry and for one that is not a plain vector graphic (a script, an embedded image or a link to another host). Both documents are `.txt` because `.dockerignore` drops `*.md` from the image. `THIRD_PARTY_LICENSES.md` is generated and lists Python packages only, so icons do not go there. Take a file unchanged from its source and check it individually: the collection states Apache-2.0 for its icon files but says nothing about the marks, and `litellm.svg` is the Twemoji "high-speed train" (CC BY 4.0), not LiteLLM's logo. `TRADEMARK.md` and `CONTRIBUTING.md` carry the rule for contributors.

### Dashboard widgets

A group on the dashboard holds links and **widgets**: cards that show one piece of live state and link to the page that explains it. `core/widgets/` owns the feature (`model` the payload every widget produces, `registry` the types that can be placed, `runtime` how a reading is taken and kept, `builtin` the types that ship with the manager, `view` what the dashboard's placeholders need), `routers/ui_widgets.py` serves the cards, `templates/partials/widgets/card.html` draws them, and `tests/test_widgets_*.py`, `tests/test_tiles_widgets.py` and `tests/test_ui_widgets.py` pin it.

| Widget id | View | Shows | Source |
|---|---|---|---|
| `core-version` | status | the installed release, and whether the last check found a newer one | `upgrade.current_version`, the cached `upgrade.cached_check` |
| `backup-age` | stat | age of the newest successful backup, overdue against the schedule | `backups`, `schedule.evaluate` |
| `disk-space` | progress | the disk that needs attention most (worst verdict, then fullest) | `host_health` |
| `services-health` | stat | running against expected services | `services.load_snapshot` |
| `open-warnings` | stat | the number of open findings, and their kinds | `notifications/detect` |
| `cert-expiry` | stat | days until the nearest certificate expires | `host_health` |

Consequences worth remembering when touching this area:

- **A widget produces a document, never markup.** `model.parse_payload` is the only way a reading becomes something the dashboard draws: `widget_api: 1` (the generation of the format, not the manager's version; another one is refused by name), a `state` (`ok`, `warn`, `critical`, `unknown`), one of four views (`stat`, `status`, `progress`, `list`) and the data for it. Every string is plain text with a limit (40, 20 or 120 characters; a list has at most 8 items; the whole document at most 64 KiB), text that looks like a tag or holds a control character is refused instead of escaped, unknown fields are dropped, and a link goes through `tiles.check_value` plus a refusal of `//host` and its backslash variant, so a link that starts with `/` always means a page of this manager. The templates never mark anything safe, so even a string that got through is escaped. The state is the widget's own verdict, drawn and never second-guessed, the way the Host page takes the core's. The built-ins return plain dicts and go through the same parser, which is what makes them the conformance test of the contract: one that drifts fails in `tests/test_widgets_builtin.py`, which reads every provider's document back through `parse_payload`.
- **One reading per type, one read at a time, and a failure is a card.** `runtime.read` keeps a reading for the type's interval (clamped between 15 and 3600 s), shares one read between everyone who asks while it runs (shielded, so a closed tab does not cancel what the next one awaits), and never raises: `WidgetUnavailableError` carries a reason for administrators, a payload the contract refuses and a read that takes longer than 40 s (just over the host check's own 30) become `unavailable`, and any other exception is logged and shown as a sentence of the template's own, because its text can hold a path or a secret. A failed read is remembered for 15 s, not the whole interval, and the last good reading is shown as `stale` ("As of 10:32 UTC") for up to 15 minutes before the card gives up. The cache is keyed by the type: the built-ins have no settings per tile, so two tiles of one type share a reading. A type that gets settings has to key on them as well. `runtime.reset_cache()` is for the tests, and they move time through `runtime._clock`.
- **The browser fetches each card on its own.** The dashboard renders a placeholder per widget (`widget_slot`, `tile_gallery.html`) that polls `GET /partials/widgets/{id}` with `hx-trigger="load, every Ns [document.visibilityState === 'visible']"`, so a slow widget costs its own card and nothing else, and a hidden tab polls nothing. The route is open to `AnyUser` and enforces the tile's visibility itself: a widget the role may not see answers 404, identical to one that does not exist, so it does not say which ids are administrators'. A tile naming a type nobody registered gets a card that says so, and a type whose requirement is not met (`WidgetType.requires`, for example the host check on a core without `doctor`) is not read at all. `GET /partials/widgets/preview/{type}` draws a type that is not placed yet for the editor's live preview, from live data; administrators only.
- **Cards read what the manager already knows and start nothing of their own.** The backup catalogue and schedule; the host check through `host_health.load_host_health`, which has its own interval and single flight, so the cards, the status row and the Host page share one `doctor`; the container snapshot through `services.load_snapshot`, which has its own few-second cache; and only the *cached* upgrade check. `run_check` and `upgrade.newer_releases` are the Upgrade page's and the notifications', they fetch, and a poll must not, so `core-version` says "No update check has run since the manager started" until somebody has opened that page, and a check made for another version than the installed one is ignored. `open-warnings` calls the notification checks' own functions (`detect.backup_overdue`, `service_findings`, `certificates` with the lead time the notifications use, `core_update` from the cached check, `addon_updates` from the catalogues on disk), so the card and the mail cannot disagree about what is wrong, and it skips the service check while `detect.stack_is_busy`, for the reason the notifications give.
- **What a plain user may be shown.** A widget can be set to everyone, so what its document names matters: `disk-space` names no path (the Host page does), `services-health` and `open-warnings` give counts and kinds of finding but no service or detail, as the status row does. A link that starts with `/` points at an administrators' page and is shown to administrators only; an absolute link is shown to everyone and opens apart.
- **A tile is a link or a widget.** `tiles.py` has `WidgetTile` next to `Tile` and `TileGroup.tiles` holds either (`kind` tells them apart). A tile without `type` is a link, so every file written before widgets reads as before, and the wire form of a link is unchanged: only a widget carries `"type": "widget"`, which is how the API body (`WidgetTileBody | TileBody`) and the editor tell them apart. A widget without a `visibility` is for administrators, where a link without one is for everyone, and an unrecognised one restricts it, like a link. `size` is `s`, `m` or `l` (one column, two, the whole row; anything else is `s`). Link tiles have no identity and widgets need one, because each is fetched by a request of its own: `_assign_widget_ids` keeps the ids written down and derives the rest from the widget's type and its place among the tiles of that type (a hash, not a random value), so loading one file twice gives the same ids; the first save writes them down. `validate_config(known_widgets=…)` refuses a widget the registry does not have, in the editor and in the raw editor, so a typo cannot be saved. A manager from before widgets reads a widget tile as a link without an address, which both the validation and the renderer refuse: a downgrade shows no widgets and refuses a save instead of silently dropping them. `with_rag_tiles` looks at links only, since a widget is not another way to reach Qdrant.
- **The editor.** `$store.tiles` (`dashboard.html`) draws a widget as a card from its type (`widgetType`, `widgetName`, the icon from `registry.ICON_PATHS`, the same closed set the dashboard uses: a widget cannot bring an image, and with it a tracking pixel). "Add widget" opens `widget-modal`: the gallery (types the installation cannot use are listed with the reason and cannot be picked), then the placement (title, width, who sees it) with the real card as the live preview, fetched through `htmx.ajax` from the preview route and escaped like any partial. `removeTile` keeps what it removed for 8 s and the unsaved-changes bar offers **Undo**, which puts it back in the same place and takes the change off the count; after the window the tile is only gone from the draft, as before. Nothing is written before **Save changes**.
- **Verified in a browser** against the real application with controlled data (no Docker stack): the six built-ins, an unregistered type, a widget that takes six seconds and one that always fails (the other eight cards answered within 100 ms while it ran), the polling intervals, an administrator's and a plain user's dashboard, the editor's add, edit, remove, undo and save (a draft holding an unknown widget is refused and named, then saved), and a 375 px viewport. Not verified: a real core's `doctor` and Docker through the widgets (replaced by fixed readings), a hidden tab (the filter is valid, the pause itself was not observed), light theme.

Not built: widgets contributed by add-ons, a widget that shows an address an administrator enters, widgets with a user interface of their own, a model usage widget (it waits for a model overview), and the `table` view. Nothing in this repository loads code or data for a widget from outside the manager. The payload and the registry are written so that these can follow without changing the built-ins: a source of data is a provider that returns the same document, and the views stay the manager's own.

### RAG connections

The page and its API (`/connections`, `/api/v1/rag/connections`) manage the ingester's connection store, `$PAPAIA_CONFIG_DIR/ai/rag/catalog/connections.yaml`. The ingester reads it as `/config/catalog/connections.yaml`, and up to `qdrant-ingest` 0.3.0 its own web interface edited it too (1.0.0 has none), so the manager shares a file it does not own with that interface and with whoever edits it by hand. `core/vectordb/` holds all of it; `tests/test_vectordb_*.py` and `tests/test_api_connections.py` pin it.

Consequences worth remembering when touching this area:

- **The format is the ingester's, exactly.** `{version: 1, connections: [{name, url, api_key?}]}`, with `api_key` as `enc:1:` plus a Fernet token whose key is the URL-safe base64 of the SHA-256 of `QI_CONNECTIONS_SECRET` (`core/vectordb/crypto.py`; the reference token in `tests/test_vectordb_crypto.py` was produced by the ingester's own code). Its entry schema forbids any other key, and a rejected entry makes it refuse the whole file at runtime: it keeps its previous set and reports `degraded`. So `type`, `default` or a timestamp are never written. `ConnectionEntry` mirrors the schema, and every candidate is validated against it before it reaches the file.
- **The default connection is the entry named `default`.** There is no second place that could drift from the file. `ensure_default()` creates it (the integrated Qdrant at `http://qdrant:6333`, the address the ingester uses, with `QDRANT_JWT_SECRET` encrypted) at start and on first use of a RAG page. It never overwrites an existing entry and never raises. It does nothing without the profile or without both secrets, and not again for a minute after a failed attempt. Its address and key are editable, it cannot be renamed or deleted, and "Reset" writes both again. While the store has no `default`, `resolve("default")` answers from `QDRANT_URL` and `QDRANT_JWT_SECRET`, so the Collections page never depends on the file.
- **`QDRANT_URL` is the manager's reach, not the ingester's.** It replaces the stored address of an entry that points at the integrated Qdrant when the manager connects (`ConnectionService._reach`), and is never written. The page shows both when they differ.
- **A stored key goes only to the address it was stored with.** Otherwise an administrator could send `QDRANT_JWT_SECRET`, which also derives the MCP tokens, to a host of their choosing. Testing a stored connection ignores an address that comes with the request, and a changed address on a connection with a key needs the key again or its removal (422). A key that is not touched keeps its stored token byte for byte, because a Fernet token is randomised and re-encrypting would rewrite the file. An address with credentials in it is refused.
- **A write is compare-and-swap.** `IngestFileRepository.update` reads the bytes, applies a mutator to the parsed document, validates, stages the result in `.connections.yaml.manager.tmp` (the ingester stages in `.connections.yaml.tmp`, which would collide), re-reads the file and swaps only if it still has the bytes the change was computed from; otherwise it computes the change again, up to three times. The mode of the file is kept, the previous content goes to `connections.yaml.bak` on a best-effort basis, the catalog directory is never created, and an `OSError` while writing is the "read-only" state. A change to an entry carries the etag of that entry rather than a fingerprint of the file, so another administrator's or the ingester's write elsewhere in the file is no conflict.
- **Problems that were already there do not lock the file.** The ingester refuses any write while the file has an error. The manager refuses only a write that introduces a new one, so the repair after a rotation of the secret (every key unreadable) stays possible. Structural damage (not YAML, not a mapping, a version other than 1, `connections` not a list) refuses everything, and the page shows it. A change is a surgery on the parsed document, so top-level keys and entries the manager does not understand stay.
- **Known limit (ingester up to 0.3.0): it does not compare before it replaces.** Its interface reads the file, edits it and replaces it. A save of its own that began before a manager save and ends after it replaces the manager's change, and the manager cannot close that window from its side. It is milliseconds wide for people saving by hand; two processes writing in a tight loop lost about half of the changes. A fix belonged in the ingester; 1.0.0 removed the interface instead, so on 1.0.0 only a hand edit can race the manager. The view of a change is taken from the file as it was right after the write, so such a loss does not turn a successful change into an error.
- **Names are fixed, jobs are checked.** Ingest jobs refer to a connection by name and nothing tells them about a rename, so a name cannot change. A delete is refused while a job in `jobs.yaml` (`jobs[*].target.connection`) uses the connection, and also when `jobs.yaml` cannot be read. Changing the address of a used connection needs `confirm_jobs`.
- **The key is never an output.** Views carry `has_key` and a state (`ok`, `none`, `unreadable`), `Connection.api_key` is out of `repr`, and the audit log records `key_action` (`set`, `none`, `kept`, `replaced`, `removed`), never a value or a token. Tests search the responses, the audit file and the log for the keys and the stored token. `unreadable` means the token does not decrypt with the current `QI_CONNECTIONS_SECRET`: it was rotated, or it is quoted (the manager's `.env` parser keeps quotes that Compose strips, and the core writes the secret unquoted). `key_drift` flags a default whose stored key is no longer `QDRANT_JWT_SECRET`.
- **TLS.** Connections are verified against the public CAs and, with `SSL_CERT_FILE`, the stack's own as well (`tls_verify`). The ingester's schema has no per-connection TLS option, so a self-signed Qdrant outside the stack is not supported.
- **Every change is audited** as `rag.connection.create`, `.update`, `.delete`, `.reset`, `.test` or `.seed` (user `manager`).
- **Verified against the real code.** A file written by the manager loads with the ingester's own `load_connections` and its keys decrypt there, and a file edited with the ingester's own writer reads back in the manager, in throwaway directories with the ingester's unmodified modules. Repeat this when the ingester's schema or cipher changes.

#### Adding a type of vector database

A type is a class that satisfies `ConnectionType` (`core/vectordb/base.py`) and is registered with `register_type`, as `QdrantType` is in `core/vectordb/__init__.py`. It declares its fields (`FieldSpec`; the dialog renders them, so the page needs no change), validates its values, turns them into the stored entry, says where the database is (`address_of`, the address a stored key is bound to) and probes it. Its `capabilities` decide where it appears: only a type with `collections` is offered on the Collections page. Two things are not generic yet, on purpose, and belong to the first second type:

- **Where its connections are stored.** The ingester reads only Qdrant entries. An entry without a type is a Qdrant, and a type the ingester cannot use should get a store of the manager's own (`manager/connections.yaml`, the same envelope plus a `type` key), so the ingester's file is never broken. `ConnectionService` talks to `IngestFileRepository` only; it is where a repository per type goes. Until the ingester's schema accepts a `type` key, the validation of every candidate refuses to write one into its file.
- **How the Collections page gets a store.** `get_store` in `routers/rag_deps.py` builds a `CollectionStore` on a `QdrantClient`. Another type brings its own store behind the same interface, or stays off the `collections` capability.

### RAG collections

The page and its API (`/collections`, `/api/v1/rag/collections`) write to the Qdrant of the selected connection as the holder of its api-key, so the only authorization is `AdminUser` and the CSRF check. Qdrant is reached through `core/qdrant.py` (plain `httpx`, no `qdrant-client`), and `core/rag_collections.py` holds the storage contract of `qdrant-mcp-rbac`. Nothing on the MCP server's side pins that contract, so `tests/test_rag_collections.py` does, against literals computed with its code.

Consequences worth remembering when touching this area:

- **One connection at a time, named in every request.** The `connection` query parameter (the default connection when absent) goes through `get_store`: an unknown name is a 404, a type without the `collections` capability a 422, and a key that cannot be read a store that explains why (a state, not an error). The partial wraps its body in an element that carries the connection it was rendered for (`data-connection`), and every change is sent to that connection, not to whatever the selector shows by then. The meta and ACL collection names and the operator role are the same on every connection.
- **Roles are editable on every connection, but enforced on one.** The stack's MCP server reads the ACL collection of the integrated Qdrant only. On a connection that does not point at it (`roles_enforced` is false) the roles are stored in the same format and the page says nothing in the stack enforces them there.
- **The roles are in the ACL collection, not in the meta collection.** `_rbac_acl` holds one point per (role, collection): id `uuid5(8c9f3b0e-4a5d-4d0a-9f1e-7d6c5b2a1f00, "<role>|<collection>")`, vector `[0.0]`, payload `{role, collection, access, doc_policy}` with `doc_policy` an explicit `null`. `_collection_meta` holds one point per collection, `{collection, embedding_model, vector_dimension}`, id `uuid5(9e3a5c2f-8b7d-4f1e-a6b3-2d8c9e4f1a02, "<collection>")`, and no roles. The MCP server skips a point it cannot parse without a word, so a payload that does not match exactly is a grant that silently does not exist. Its own `AGENTS.md` states the id formula differently; its code is authoritative.
- **Access levels.** `r` and `rw` are per collection. `m` is global manage: the MCP server returns a manage token for any role that holds one, whatever the `collection` field says, and `*` is only the convention. The page lists those under "Access to every collection" and never edits them, and neither lists nor deletes an `m` grant that names a collection.
- **Nothing cascades in Qdrant, and the ids are deterministic.** Deleting a collection leaves its meta point and its grants behind, and re-creating the name would revive the grants. `delete` removes all three and is idempotent, so a delete that stopped half-way is finished by repeating it. `create` removes what it wrote if a step after the collection exists fails.
- **An access change keeps `doc_policy`.** The policy is not edited here, but another tool may have set it; a changed point keeps its id and its policy, and an unchanged role is not written again.
- **The ingest operator role is never listed per collection.** It always has access to every collection, so it is shown locked, refused in a role list (422), and its `r`/`rw` points are hidden. A global `m` grant `(role, "*", "m")` makes the MCP server treat it as manage; it is written with every change and from the banner when it is missing. Changing `QI_OIDC_OPERATOR_ROLE` does not remove the grant of the old name, and the Keycloak realm still only knows `qdrant-ingest-operator`.
- **Names come from two places that the core does not tie together.** The MCP server reads `EMBEDDING_META_COLLECTION` and `RBAC_ACL_COLLECTION`, the ingester `QI_EMBED_META_COLLECTION` and `QI_RBAC_ACL_COLLECTION`; the manager follows the MCP server's name first and warns when the two disagree. The core passes none of them on to the MCP server, so a changed name takes effect for the ingester only. Until it does, changing the names is not supported.
- **A collection created without a model is open to any model.** The ingester writes the meta point at the end of its first run and refuses a later run whose model differs from a recorded one. Creating with a model makes it text-searchable through the MCP server straight away, and binds ingest jobs to that model.
- **System collections are invisible.** The two configured names are never listed, created, deleted or given roles. A new collection cannot start with an underscore, which the services reserve for theirs. Collections the ingester created may have names this page would not accept, so deleting and editing roles accept any existing name.
- **Role names are exact.** The MCP server matches them case-sensitively against the realm and client roles of the token. They are trimmed, but not otherwise changed, and `|` is refused because it separates role and collection in the point id.
- **The profile is checked after the role.** `RagAdmin` resolves `AdminUser` first, so a signed-out browser still gets the login redirect and a non-admin the 403; only an administrator on a deployment without the profile gets the 404.
- **Qdrant being unavailable is a state, not an error.** An unreachable Qdrant, a refused key and a missing key become a reason on the page (`CollectionsView.available`), and a write answers 503. The api-key is never part of a message, a log line or an audit entry. A collection that disappears between the listing and its detail call is still listed, without numbers.
- **Every change is audited** as `rag.collection.create`, `rag.collection.delete`, `rag.collection.roles.update` or `rag.collection.operator-grant`, with the collection as target (`*` for the grant). The grant is audited only when it was actually written.
- **Verified against the real code.** The grants and meta points the manager writes were read back with `qdrant-mcp-rbac`'s own loader and token builder (including the operator role resolving to global manage), and `qdrant-ingest`'s writer accepted the collections and enforced model and dimension, against a throwaway Qdrant. Repeat this when either contract changes.

### RAG embedding

The page and its API (`/embedding`, `/api/v1/rag/ingest`) put files into a collection through the ingester. `core/ingest/` holds all of it; `tests/test_ingest_*.py` and `tests/test_api_ingest.py` pin it, against `tests/fake_ingest.py`, a fake that reads the real `jobs.yaml` on a reload.

Consequences worth remembering when touching this area:

- **The ingester can only run what `jobs.yaml` declares and cannot be handed a file.** So the manager keeps two jobs per (connection, collection) in `ai/rag/catalog/jobs.yaml`, one per kind of source, with the id prefix `mgr-` (`catalog.managed_job_id`). Only entries with that prefix are ever written; everything else in the file stays as the operator (or, up to `qdrant-ingest` 0.3.0, the ingester's own interface) left it. The job is manual-only and its stored mode is `append`, which cannot delete or update, so a run started outside the manager can do no harm; the manager chooses the real mode in each run request. The upload job's path is changed for every run, and a path that no longer exists scans as empty.
- **A document's identity is the job, the source label and the path inside the source.** The ingester derives every point id from them, which is why the job ids and the labels (`manager-upload`, `manager-folder`) are stable and why uploading the same relative path again replaces a document instead of adding a copy. The state rows outlive the files, so this holds after the staged files are gone.
- **Add and update needs `delete_vanished: false` (`Fidonis/qdrant-ingest#41`).** Without it `upsert` removes every source that is missing from the scan, and the staged files are gone after each run. An ingester without the option answers a run request carrying it with 422 `extra_forbidden`; `IngestClient.supports_update_without_delete` finds that out with a request for a job id no job can have (`_probe`, answered 404 by a new ingester and 422 by an old one), so nothing is started to ask. Replace works with any ingester that has `full_scope: collection`.
- **The ingester refuses a catalog with one invalid job as a whole and keeps serving the previous one.** So a job that exists after a reload proves nothing: `_loaded_as_written` compares the served definition with what was written, and a mismatch rolls the write back (`JobsFileRepository.restore`, which refuses to overwrite somebody else's later change). The cross-job rules (one connection and one model per collection, distinct labels, the connection exists) are checked before the write (`catalog_problems`); They were compared with the ingester's own loader when this was written (see the last item).
- **The file is rewritten, not edited.** Comments and blank lines in `jobs.yaml` are lost on a write; the previous content is kept as `jobs.yaml.bak` and nothing is written when the entry is already right. The writer shares its compare-and-swap with the connection store (`vectordb/catalog_io.py`).
- **Paths are jailed by construction** (`documents.py`): plain segments only, every segment `lstat`-ed on the way down from a root resolved once, a symbolic link anywhere refuses the path, the staging area is hidden from the folder tree and from every selection of it, and a name with `*` or `?` is refused because the ingester's glob dialect has no escape. The folder job always carries `exclude: uploads/**`, so a selection of the whole folder cannot read another administrator's upload. Tests that need a link are skipped where the platform cannot create one; run them on Linux.
- **An upload is a loan, not storage** (`uploads.py`): one staging folder per owner and upload (`uploads/<owner>/<id>/`, `0700`/`0600`), a manifest outside the documents folder (the ingester would embed it), names checked rather than repaired, limits enforced while the bytes arrive, removal folder first and record second. It is removed after a run with status `success` and no failed document, kept for a retry otherwise, and removed by the time limit whatever its state, except while its run is verifiably still working. The multipart body is read inside the handler after the role and CSRF checks, because FastAPI parses a declared body before it looks at who sent it.
- **Cleaning up does not depend on a browser.** `reconcile` applies the rules and is called by the status strip when it sees a run end and by `IngestWatcher`, a task built in the startup hook (every few seconds while an upload is being embedded, once a minute otherwise). It writes nothing but what a manifest records, so a restart or two passes at once lose nothing. It assumes one process.
- **The status is the ingester's** (`GET /v1/runs`), so it survives a restart of the manager. The ingester writes its counters when a run ends, so while one works the page shows the points written so far, counted in Qdrant by `ingest_run` (`CollectionStore.count_run_points`); that is a hint and may be absent. An abort is cooperative and takes effect between documents, which the page says.
- **One run per collection, over both kinds of source**, because the upload job's path is the run's source. None starts while a restore, an upgrade or a stack action runs.
- **The token is never an output.** `QI_API_TOKEN` is read from `ai/rag/.env` at request time (`RagSecrets.ingest_api_token`) and goes into one header. Audit entries (`rag.ingest.upload.*`, `rag.ingest.run.*`) carry counts and ids, never file names.
- **A custom `QI_LOCAL_MOUNT` is invisible to the manager** unless it lies inside the configuration or workspace directory; `documents_dir` says so and the page disables what depends on it. A backup of the configuration directory contains an upload that is still staged; excluding `ai/rag/documents/uploads` there is a change in the core.
- **Verified against the real code.** The jobs the manager writes load with the ingester's `load_catalog`, its include globs select exactly the intended files under the ingester's `scan_tree`, and a run through the real ingester and Qdrant (add, update by path, unchanged file, folder source, replace, failure with retry, a refused catalog, abort) behaved as described. Repeat this when the ingester's job schema, glob dialect or run options change.

### RAG ingest jobs

The pages (`/ingest/jobs`, `/ingest/jobs/{id}`, `/ingest/new`, `/ingest/jobs/{id}/edit`, `/ingest/runs`, `/ingest/runs/{id}`, `/ingest/secrets`, `/ingest/orphans`, `/ingest/catalog`) and their API (`/api/v1/rag/ingest/...`, `routers/api_ingest_jobs.py`) manage the ingester's catalog. `core/ingest/jobs_service.py` does what the routes ask and is the only thing they call; `tests/test_ingest_*.py`, `tests/test_api_ingest_jobs.py` and `tests/test_ingester_contract.py` pin it, against `tests/fake_ingest.py`.

Consequences worth remembering when touching this area:

- **`jobs.yaml` has several writers and none of them owns it.** This editor, the Embedding page (`mgr-` jobs), a person with a text editor and, up to `qdrant-ingest` 0.3.0, the ingester's own interface all write it. Every manager write goes through `JobsFileRepository` (`update(mutate, rules)`, `put_job`, `remove_job`, `set_enabled`, `set_defaults`, `replace_raw`, `restore`) and the compare-and-swap of `vectordb/catalog_io.py`; the change is computed again from the bytes that are there when the swap fails. An editor's save carries the `entry_etag` of the entry it opened, so a change to another job is no conflict and one to this job is a 409.
- **The mirror is not the ingester.** `jobspec.JobSpec` copies the ingester's job schema, defaults and cross-job rules so the editor can check a job without the ingester and the manager can say what a job inherits. Where the two differ, the ingester wins at runtime, which is why a write is never trusted: `catalog_load.reload_and_verify` makes the ingester reload and compares what it serves with what was written (`loaded_as_written`, `subset_matches`). `tests/test_ingester_contract.py` compares field sets, defaults, the rules that refuse a job and the secret store's format against the ingester's own modules; it needs `QDRANT_INGEST_SRC` (the ingester's `src` directory) and is skipped without it. Run it when either schema changes.
- **All or nothing, and what that means for a save.** The ingester keeps its previous catalog when any job is invalid (`applied: false`), and at its start loads the valid subset. So after a write the manager distinguishes "the ingester refuses my job" (the write is taken back) from "it refuses other jobs" (the write stays, and the result says the previous catalog is still served, with `elsewhere` naming the jobs). With the ingester unreachable a job is checked by the manager's rules, saved, and the result says it could not be confirmed. A job that is in `jobs.yaml` is never an orphan, however it is served; a leftover is a state row whose id is in no file.
- **The editor works on the effective job.** `jobspec.effective` merges the catalog defaults over a job and `minimise` writes back only what differs from them, except `source`, `target`, `mode` and `embedding.model`, which are always written: a collection is bound to its model, and a changed default must never move a job to another one. A key the editor does not know stays as it was.
- **Ids are for life.** Every point derives from the job id, the source label and the path, so an id cannot change in an edit (duplicate instead), `mgr-` (the Embedding page's) and `new` are reserved, and re-creating a deleted job with the same id, label and path adopts what is left of it. Pausing is `enabled: false`; the ingester also has a pause of its own (`paused` in its job list), which the list shows and *Resume scheduling* clears.
- **Schedules are in the ingester's dialect, not the backup schedule's.** `schedules.py` is separate from `schedule.py` on purpose: the ingester feeds a cron expression to APScheduler's `CronTrigger.from_crontab`, which counts weekdays from Monday (0) and ANDs day-of-month with weekday. The manager always writes weekday names and reads numbers the way the ingester does, so what the editor shows and what runs agree; the "next runs" come from the ingester. An interval schedule keeps its timer across a catalog reload (an ingester change).
- **Credentials.** A value goes in `ai/rag/catalog/secrets.yaml` (`version: 1`, `secrets: [{name, value}]`, `value` = `enc:1:` + Fernet token keyed from `QI_CONNECTIONS_SECRET`, the same cipher as the connection store) and is write-only: no view, log line, audit entry or response carries it. The writer is compare-and-swap, keeps no `.bak` (a backup copy of a secret would be one more place for it), and the ingester reads the file when a value is needed, so a new credential works without a restart. The ingester answers `${env:QI_SECRET_X}` from its process environment first and the file second, and the manager follows that: a name defined in `ai/rag/.env` is never shadowed, and the manager knows the names from that file only, not from an environment it cannot see. A credential a job refers to cannot be deleted. This is the same level of protection as `connections.yaml`: the key is in the `.env` next to it.
- **What the ingester can do decides what the page offers.** `/health.features` lists `run_progress`, `documents`, `validate`, `delete_runs` and `secret_store`. An ingester without one keeps working: no progress, a files tab that explains, the manager's own checks, runs that stay when a job is deleted, no stored credentials. `qdrant-ingest` 1.0.0 reports all five; 0.3.0 has none of them.
- **A run is the ingester's, a page is a view of it.** The list polls only while a run works (the partial renders its own `hx-trigger` conditionally), the runs and the files come from the ingester's REST API, and the ingester's records survive a restart of the manager. An abort is cooperative and takes effect between two files.
- **A job's runs go with it, and can go without it.** The ingester prunes a job's history only after one of the job's own runs, so the runs of a deleted job would stay for good; `JobsService.delete` therefore also calls `DELETE /v1/jobs/{id}/runs` (`IngestClient.delete_runs`), and only after the reload shows the ingester no longer serves the job (while another job is invalid it keeps its previous catalog and the job with it, and a run could still write to the history). Each step reports into the note and none stops the others. `delete_runs` deletes a job's history for whole days, both included, converted to `[start, end)` instants in the ingester's zone (`display.day_bounds`: UTC with an explicit `+00:00`, never `Z`, because the ingester compares the stored text), counts first (`dry_run`), and works for a job that no longer exists. A run that is working is never deleted; the ingester refuses it in the same statement, so a run that starts meanwhile is safe, and the answer counts it. It is `POST .../runs/delete`, not a `DELETE`, because `DELETE /job-runs/{id}` aborts a run. What the job embedded and the ingester's `documents` rows are not touched; the time of the job's last run is, which can make a `run_on_startup: if_missed` job start at the next start of the ingester. The jobs of the Embedding page can be deleted too (the next embedding writes the job again, an upload that still waits keeps its files until the time limit because `reconcile` keeps an upload whose run is unknown); they still cannot be edited or paused.
- **Page scripts.** `htmx` and `alpine` are deferred scripts, so an inline script must not call `htmx` while the page is parsed (the job page starts its first tab after `DOMContentLoaded`; a test pins it). A `<select>` whose options an Alpine `x-for` makes shows its first option whatever the model holds, because `x-model` is applied before the options exist; such selects carry `x-effect="sync($el, ...)"`, and a test checks that they all do. Unit tests with a `TestClient` cannot see either, so look at a page in a browser when you change one. The editor asks before a link leaves it with unsaved changes in its own dialog (`guardLink`, `#leave-editor`); a page cannot replace the browser's prompt for a reload, a closed tab or the back button, so `beforeunload` stays as the fallback.
- **Every change is audited** as `rag.ingest.job.create|update|delete|enable|disable|resume|run`, `rag.ingest.run.abort|delete`, `rag.ingest.orphan.delete`, `rag.ingest.secret.set|delete`, `rag.ingest.defaults.update` or `rag.ingest.catalog.raw`, with counts and ids and never a value.
- **Verified against the real code.** What the editor produces loads with the ingester's `load_catalog` and what the ingester refuses is refused here (the contract test), and the pages were driven in a browser against the real ingester and a throwaway Qdrant: runs with progress and an abort, a dry run, a rebuild, a failed fetch, a stored credential making a job valid without a restart, an invalid job kept out by the ingester and repaired, a leftover adopted by a job of the same id, an edit that raced another, an ingester that is down and one without the new features. The deletion of runs was driven the same way: a period in the dialog (counted, then deleted, the list refreshed), the history of a job that was deleted earlier, a job deleted with its runs, an Embedding page job deleted with its runs, a job that the ingester kept serving because another job was invalid (its runs stayed, the note said why), and the 0.3.0 image without `delete_runs` (no menu item, the dialog says the runs stay). Repeat this when the ingester's REST API or the page scripts change.

Known limits: the ingester up to 0.3.0 does not compare before it replaces a file, so a save of its own interface that began before a manager save and ends after it replaces the manager's change (1.0.0 has no interface); the editor offers what the ingester's job schema has (the nine source types and their fields; any other rclone option goes into the free-text flags field); a run's history is the ingester's last 200 per job, unless it is deleted sooner, and an ingester without `delete_runs` keeps the runs of a deleted job.

## Engineering conventions

### Branches

| Prefix | Use |
|---|---|
| `feat/<short>` | New user-facing feature |
| `fix/<short>` | Bug fix |
| `docs/<short>` | Documentation only |
| `refactor/<short>` | Refactoring without behaviour change |
| `test/<short>` | Test additions or fixes |
| `ci/<short>` | CI/CD configuration |
| `chore/<short>` | Maintenance |

Never push directly to `main`; always open a pull request.

### PR titles — Conventional Commits

Format: `<type>[(<scope>)][!]: <subject>`

- Subject: lowercase, imperative mood, no trailing period
- `!` suffix marks a breaking change (triggers a major version bump)
- CI enforces this format on every PR

### Merge strategy

All PRs are **squash-merged**. The PR title becomes the single commit message on `main`.

## Code style and local checks

Run all checks locally before pushing:

```bash
# From the repository root: the two checks CI runs from there
yamllint .
uv run --project src ruff check .

# From src/
cd src
uv run mypy .
uv run pytest -q
```

- **Python linting**: ruff with rule sets E, F, I, B, UP, N, RET, SIM, ASYNC. Run it from the
  **repository root**, as CI does (`ruff check .` with the root `ruff.toml`): `tests/` is a
  sibling of `src/`, so `uv run ruff check .` from inside `src/` lints `src/` only and passes
  over a line in a test that CI then rejects. The `--project src` above only borrows the
  environment `uv sync` made there.
- **Type checking**: mypy in strict mode; all public functions must carry explicit type annotations
- **Import style**: absolute imports (`from app.config import get_settings`)
- **YAML**: yamllint with the project `.yamllint` config
- **Python version**: 3.12 minimum
- **Tests that need another checkout** are skipped without it: `tests/test_ingester_contract.py` needs
  `QDRANT_INGEST_SRC` (the `src` directory of a `qdrant-ingest` checkout), `tests/test_mail_contract.py` and
  `tests/test_config_contract.py` need `PAPAIA_SRC` (a checkout of the papAIa core that has the mail relay and the
  module operations). Run them with the latest release of the other repository whenever either side changes. The
  tests that need a symbolic link or read a file mode are skipped on Windows; run them on Linux.

`docker/.env.example` only because compose needs it to place the path-parity
mount.

## Security boundaries

- **Never log** session secrets, OIDC client secrets, the mail relay's upstream password, catalog tokens, Qdrant api-keys (`QDRANT_JWT_SECRET` and the keys stored in connections), `QI_API_TOKEN`, `QI_CONNECTIONS_SECRET`, `LITELLM_MASTER_KEY`, the values of ingest credentials, the webhook URLs of notification recipients or the content of overlay files (it can hold an API key). They are never part of a response or an audit entry either.
- **The signed-in user's access token** (used by the Users page) lives in memory only: never in the session cookie, a response, an audit entry or a log line. Temporary passwords are returned once and are never part of an audit entry or a log line.
- **docker.sock access is root-equivalent.** The manager container mounts `/var/run/docker.sock`. This is required for Compose operations and is intentional — the manager profile is off by default.
- **Subprocess inputs are whitelisted.** All calls to `papaia-ctl` go through `core/ctl.py` which validates the verb against an allowlist and uses arg arrays (never `shell=True`). The commands that write, the core's `setup` and `module-purge`, have an allowlist of their own and are reachable only through `run_smtp_setup` and `run_module_setup` (the options of the mail relay or of one optional module) and `run_module_purge` (one module's volumes and settings, never while it is on).
- **Copyleft dependencies are not accepted.** The CI license-check workflow rejects GPL, LGPL, AGPL, EUPL, and similar licences.
