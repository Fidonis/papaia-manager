{# ── The action-placement contract ──────────────────────────────────────── Three tiers. Every function button in this panel belongs to exactly one of them, and the tier decides where it sits: 1 page action sticky header, right of the status chip, via `{% block page_actions %}`. Exactly one filled primary button per page, optionally one outline secondary; everything else goes into `overflow_menu`. 2 row action right-aligned in the row or the card footer, wrapped in `row_actions`. At most two visible buttons, ordered [state verb, filled] [secondary verb, outline]. Every destructive verb -- remove, uninstall, delete, restore -- goes into `overflow_menu` and confirms in a dialog. 3 bulk action `bulk_bar`, pinned to the bottom edge for as long as a selection exists. The one place "at the bottom" is the right answer: the bar belongs to a selection made in the list above it and must not be scrollable away from it. Button vocabulary, so the same verb reads the same everywhere: primary / state verb btn btn-primary btn-sm (btn-xs in a dense row) secondary verb btn btn-outline btn-sm start btn btn-success btn-sm stop btn btn-warning btn-sm destructive menu item with `class="text-error"` Both wrappers are `{% call %}` macros rather than data-driven item lists: every call site carries its own Alpine expression and its own job-polling callback, and squeezing those through a list of dicts would be harder to read than the markup it replaces. Class names are spelled out per branch and never assembled from a variable. app.css is built by scanning these templates, so a computed class name does not survive the purge -- same rule as _group_controls.html.
